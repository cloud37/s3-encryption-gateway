## 1. Context & Current State

Both SigV2 query authentication (`internal/api/auth.go:326-368`) and header
authentication (`internal/api/auth.go:371-401`) call `buildV2StringToSign`.
That helper builds `CanonicalizedResource` from only `r.URL.Path`, with `/` as a
fallback (`internal/api/auth.go:407-452`). It omits all query subresources. A
signature accepted for `/bucket/key` is consequently also accepted after adding
`?acl`, while a standards-compliant client that signed `/bucket/key?acl` is
generally rejected. This permits semantic substitution because SigV2 is meant
to append recognized S3 subresources to the canonical resource [1].

The omitted fields select materially different gateway operations before the
generic routes. Multipart routing uses `uploads`, `uploadId`, and `partNumber`
(`internal/api/handlers.go:257-264`); object retention, legal hold, tagging, ACL,
restore, and select routes use query selectors
(`internal/api/handlers.go:266-288`); bucket configuration routes use
`object-lock`, `lifecycle`, `policy`, `cors`, `versioning`, `encryption`, `acl`,
`location`, `notification`, `replication`, `logging`, `requestPayment`,
`website`, `inventory`, `analytics`, and `intelligent-tiering`
(`internal/api/handlers.go:290-366`); DeleteObjects is selected by `delete`
(`internal/api/handlers.go:377-379`). `versionId` also changes which object
generic GET, HEAD, and DELETE handlers address (`internal/api/handlers.go:916,2327,2412`).

The gateway already has a SigV2 policy gate in `AuthMiddleware`
(`internal/api/auth_middleware.go:132-147`), but configuration defaults it on
(`internal/config/config.go:980-983`). The field claims an
`AUTH_ALLOW_LEGACY_SIGNATURE_V2` environment mapping
(`internal/config/config.go:738-745`), while environment loading handles only
clock skew (`internal/config/config.go:1647-1652`). Helm exposes only clock skew
and credentials (`helm/s3-encryption-gateway/values.yaml:168-187`) and renders no
SigV2 policy variable (`helm/s3-encryption-gateway/templates/deployment.yaml:71-82`).
AWS has deprecated SigV2 and recommends SigV4 [2], so the repaired legacy mode
must become an explicit opt-in rather than the default.

The existing SigV2 tests generate expected signatures through the same flawed
production helper (`internal/api/auth_test.go:707-745,801-861`) and therefore do
not independently prove wire compatibility. The SEC-40 conformance request also
includes `response-content-type` but omits it from its manual string-to-sign
(`test/conformance/auth_test.go:26-53`); that test must be corrected when signed
response overrides are enforced.

## 2. Design Goals & Non-Goals

### Goals

1. **Complete semantic binding** — every query key that selects a gateway S3
   operation or object version is authenticated when SigV2 is enabled.
2. **Standards-compatible canonicalization** — preserve the escaped resource
   path, include only the explicit signed allowlist, sort names
   lexicographically, and format empty and valued parameters per S3 SigV2.
3. **Ambiguity rejection** — malformed queries and duplicate signed parameters
   fail authentication rather than selecting an arbitrary value.
4. **Both authentication forms** — header and presigned SigV2 use exactly the
   same canonicalized-resource helper.
5. **Safe default** — new/default configurations reject SigV2; operators can
   explicitly opt in through YAML, environment, or Helm.
6. **Compatibility clarity** — ordinary unsigned list/filter query parameters
   remain excluded as required by SigV2, and the breaking default change is
   documented prominently.
7. **Independent vectors** — tests use literal expected canonical resources and
   signatures rather than relying only on production helper output.

### Non-Goals

1. **No SigV2 redesign** — the gateway will not sign arbitrary query parameters;
   doing so would be incompatible with existing SigV2 clients.
2. **No virtual-host-style routing** — public routes are path-style, so this
   issue does not derive or prepend a bucket from `Host`.
3. **No indefinite legacy support promise** — explicit opt-in is transitional;
   complete SigV2 removal can be proposed separately after usage data permits.
4. **No credential migration** — the same access/secret keys can sign SigV4;
   only client signing configuration changes.
5. **No unrelated SigV2 header canonicalization cleanup** — the `x-amz-date`
   Date-line behavior is tracked as a follow-up unless an independent failing
   AWS vector proves it must be corrected for these tests.

## 3. Target Interface / Semantics / Behaviour

### Canonicalized resource API

```go
var sigV2CanonicalResourceParams = map[string]struct{}{
    "acl": {}, "analytics": {}, "cors": {}, "delete": {},
    "encryption": {}, "intelligent-tiering": {}, "inventory": {},
    "legal-hold": {}, "lifecycle": {}, "location": {}, "logging": {},
    "notification": {}, "object-lock": {}, "partNumber": {},
    "policy": {}, "replication": {}, "requestPayment": {},
    "response-cache-control": {}, "response-content-disposition": {},
    "response-content-encoding": {}, "response-content-language": {},
    "response-content-type": {}, "response-expires": {}, "restore": {},
    "retention": {}, "select": {}, "select-type": {}, "tagging": {},
    "torrent": {}, "uploadId": {}, "uploads": {}, "versionId": {},
    "versioning": {}, "versions": {}, "website": {},
}

func buildV2CanonicalizedResource(r *http.Request) (string, error)
func buildV2StringToSign(r *http.Request) (string, error)
```

The set combines the historical AWS SigV2 S3 subresources and response-header
overrides [1] with the exact additional S3 operation selectors currently routed
by this gateway (`internal/api/handlers.go:257-379`). Later S3 features postdate
SigV2, but accepting SigV2 for those routes without signing their selectors
would preserve the vulnerability. New routing-sensitive query keys must be
added to this allowlist in the same change that registers their route.

Rationale: an explicit private allowlist avoids signing ordinary query fields
that SigV2 intentionally excludes while ensuring complete mediation for every
gateway operation selector.

### Canonicalization algorithm

Given a request, the helper must:

1. Use `r.URL.EscapedPath()` exactly as transmitted, defaulting to `/`; do not
   clean, decode, case-fold, or re-encode the path.
2. Parse `r.URL.RawQuery` with `url.ParseQuery` and return an error for malformed
   escapes or other parse failure.
3. Select only exact, case-sensitive keys in `sigV2CanonicalResourceParams`.
4. Reject any selected key with more than one value, including one empty and one
   non-empty occurrence.
5. Sort selected names lexicographically by byte value.
6. Render an empty value as `name` and a non-empty decoded value as
   `name=value`; do not URL-encode the value again.
7. Append selected entries as `?entry&entry` to the escaped path.
8. Exclude authentication fields (`AWSAccessKeyId`, `Signature`, `Expires`,
   `Date`) and ordinary list/filter fields such as `prefix`, `delimiter`,
   `marker`, `max-keys`, and `continuation-token`.
9. Never mutate `r.URL`, `RawQuery`, or parsed value slices.

Examples:

| Request target | Canonicalized resource |
|---|---|
| `/bucket/key` | `/bucket/key` |
| `/bucket/key?acl` | `/bucket/key?acl` |
| `/bucket/key?uploadId=u%2B1&partNumber=2` | `/bucket/key?partNumber=2&uploadId=u+1` |
| `/bucket?prefix=a&delete=` | `/bucket?delete` |
| `/bucket/key?response-content-type=text%2Fplain` | `/bucket/key?response-content-type=text/plain` |

`ValidateSignatureV2` propagates canonicalization errors from both auth forms
before signature comparison. Middleware maps them to its existing opaque
`SignatureDoesNotMatch` response and does not dispatch downstream.

Rationale: deterministic sorting and unambiguous duplicate rejection ensure the
authenticated semantics equal the router-visible semantics rather than merely
matching one parser's first-value behavior.

### Configuration contract

```yaml
auth:
  allow_legacy_signature_v2: false
```

| Surface | Name | Default | Validation |
|---|---|---|---|
| YAML | `auth.allow_legacy_signature_v2` | `false` | Boolean |
| Environment | `AUTH_ALLOW_LEGACY_SIGNATURE_V2` | unset, therefore `false` | `strconv.ParseBool`; invalid values fail config loading |
| Helm | `config.auth.allowLegacySignatureV2.value` | `"false"` | String boolean or `valueFrom` |

Explicit `true` preserves repaired SigV2 support. Explicit `false` and omission
reject SigV2 before signature validation. Existing deployments relying on the
old implicit `true` must opt in or migrate clients and outstanding presigned
URLs to SigV4. No stored data or credential format changes.

Rationale: AWS has deprecated SigV2 in favor of SigV4 [2]; default denial
reduces exposure to a legacy protocol whose canonicalization intentionally does
not cover arbitrary query parameters.

## 4. Work Breakdown

### Phase A — Canonicalized-resource implementation

- A1. **Edit `internal/api/auth.go`:** define the immutable private allowlist and
  add `buildV2CanonicalizedResource`. Change `buildV2StringToSign` to return
  `(string, error)`, append the helper result, and propagate errors through both
  branches of `ValidateSignatureV2`.
- A2. **Edit `internal/api/auth_test.go`:** update existing callers for the error
  return and add `TestBuildV2CanonicalizedResource`,

  `TestBuildV2CanonicalizedResource_MalformedQueryRejected`, and
  `TestBuildV2CanonicalizedResource_QueryNamesAreCaseSensitive`. Expected
  resources must be literals, not values generated by the production helper.

### Phase B — Mutation-resistant authentication tests

  `TestValidateSignatureV2_HeaderAuth_SubresourceMutationRejected`,

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Existing SigV2 clients and presigned URLs fail after upgrade | Document the breaking default, provide YAML/env/Helm opt-in, keep repaired SigV2 functional, and add an upgrade inventory step. |
| Allowlist omits a routed operation and preserves substitution | Table-test every key represented by `RegisterRoutes`; require future query-routed operations to update the allowlist and test in the same change. |
| Extra nonstandard keys break standards-compliant clients | Add only gateway-routed S3 operation selectors plus documented response overrides; continue excluding ordinary list/filter fields. |
| Path decoding differs from client signing | Use `EscapedPath()` and literal encoded-path vectors matching the S3 canonical resource contract. |
| Duplicate query values select different semantics across parsers | Reject duplicates for every signed key before signature comparison. |
| Environment typo silently disables or enables legacy auth | Parse with strict boolean validation and fail configuration loading on invalid input. |
| Existing SEC-40 conformance test fails after correct canonicalization | Update its independent literal string-to-sign to include the signed response override while preserving its redaction assertions. |
| Tests reproduce the production bug in their signer | Use literal canonical-resource expectations and at least one independently calculated AWS-compatible HMAC vector. |

## 8. Definition of Done

- [ ] Per `docs/issues/v1.0-issues.md:244-273`, adding, removing,
      substituting, or changing any allowlisted routing-sensitive query key
      invalidates both header and presigned SigV2 authentication.
- [ ] The allowlist covers every query selector registered at
      `internal/api/handlers.go:257-379`, including `delete`, `uploadId`,
      `partNumber`, `versionId`, tagging, ACL, retention, and bucket policy.
- [ ] Canonicalization preserves escaped paths, matches names case-sensitively,
      sorts names, renders empty/value forms exactly, and rejects duplicate or
      malformed signed parameters.
- [ ] Authentication parameters and ordinary list/filter query fields remain
      excluded and compatible with standards-compliant SigV2 clients.
- [ ] SigV2 defaults to disabled in binary and Helm defaults; explicit YAML,
      valid environment, literal Helm value, and `valueFrom` opt-ins work.
- [ ] Invalid `AUTH_ALLOW_LEGACY_SIGNATURE_V2` values fail configuration loading
      rather than being silently coerced.
- [ ] Middleware tests prove a rejected substitution never invokes the changed
      downstream route.
- [ ] Independent literal vectors, not only production helper calls, verify the
      canonical resource and HMAC.
- [ ] New canonicalization code in `internal/api` has at least 85% statement
      coverage and `FuzzBuildV2CanonicalizedResource` is seed-covered by Tier 1.
- [ ] SEC-44 Tier 2 tests cover both SigV2 presigned and header authentication,
      are registered with `CapObjectTagging` or `CapObjectACL`, never branch on
      provider names, and explicitly opt in to SigV2.
- [ ] Tier 2 substitution cases assert `SignatureDoesNotMatch`, verify persistent
      tagging/ACL state is unchanged, use unique resources, and clean up with
      `t.Cleanup`.
- [ ] `config.yaml.example`, `README.md`, `docs/DEPLOYMENT.md`, Helm README, and
      `CHANGELOG.md` document opt-in and upgrade consequences.
- [ ] `make test` and then `make test-conformance` pass with logs captured at the
      paths in the Validation Matrix.
- [ ] `make test-isolation-check` passes after the conformance files are final.

1. Verify and, if necessary, correct SigV2's `x-amz-date` Date-line semantics
   against independent AWS vectors; this is separate from resource
   canonicalization and should not expand SEC-44 without a failing vector.

   later introduces corresponding host-based bucket routing.
