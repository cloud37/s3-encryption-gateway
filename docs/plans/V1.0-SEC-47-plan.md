## 1. Context & Current State

The credential model separates bucket creation/deletion from object access but
defines only `create` and `delete` bucket grants
(`internal/config/config.go:754-769`). `Credential.CanWrite` reflects only the
object `rw` permission (`internal/api/credential_store.go:58-67`). The
authorization classifier maps all 14 bucket subresource PUT routes to ordinary
`authorizationWrite` (`internal/api/authorization.go:120-133,232-235`), so an
in-scope `rw` credential can alter bucket ACL, CORS, encryption, inventory,
lifecycle, logging, notification, policy, replication, request payment,
versioning, website, intelligent tiering, and Object Lock configuration through
the gateway's more privileged backend credentials.

Thirteen PUT handlers are raw passthroughs
(`internal/api/handlers.go:6230-6395`); Object Lock has a dedicated bounded
parser (`internal/api/object_lock.go:392-449`). Raw passthrough defaults to no
limit (`internal/api/utils.go:276-288`) and `forwardToBackend` then executes an
unbounded `io.ReadAll` (`internal/api/utils.go:164-174`). This plan adds an
independent `manage` grant for bucket configuration PUT/DELETE and applies a
shared 1 MiB control-plane body limit to raw handlers. Reads continue to use
object `ro`/`rw` plus bucket scope; CreateBucket and DeleteBucket retain their
independent grants and `allow_bucket_creation` behavior.

## 2. Design Goals & Non-Goals
### Goals
1. **Least privilege** — object `rw` grants no bucket configuration mutation.
2. **Explicit administration** — every bucket configuration PUT/DELETE requires `bucket_permissions: [manage]`.
3. **Scope preservation** — `manage` never bypasses bucket patterns or `proxied_bucket`.
4. **Lifecycle separation** — `create`, `delete`, and `manage` remain independent grants.
5. **Bounded control bodies** — raw bucket configuration bodies are rejected above 1 MiB before backend contact.
6. **Route completeness** — authorization tests enumerate the registered bucket mutation routes.

### Non-Goals
1. Granting object writes through `manage`; object permissions remain separate.
2. Changing read authorization for bucket configuration.
3. Parsing or semantically validating every backend-specific XML document.
4. Applying the global `allow_bucket_creation` switch to configuration updates; explicit per-credential `manage` is the gate.

## 3. Target Interface / Semantics / Behaviour

```go
const (
    BucketPermissionCreate BucketPermission = "create"
    BucketPermissionDelete BucketPermission = "delete"
    BucketPermissionManage BucketPermission = "manage"
)

const maxBucketConfigurationBody int64 = 1 << 20
```

Add `authorizationManageBucket`. Bucket-level PUT/DELETE selector routes return
that operation; middleware requires matching bucket scope and `manage`.

| Request class | Required permission |
|---|---|
| object mutation / MPU | object `rw` |
| CreateBucket | bucket `create` + global creation gate |
| DeleteBucket | bucket `delete` |
| bucket configuration PUT/DELETE | bucket `manage` |
| bucket configuration GET/HEAD | object `ro` or `rw` |

Raw bucket configuration handlers call
`handlePassthroughWithBodyLimit(..., maxBucketConfigurationBody)`. Object Lock
retains its stricter 100 KiB parser limit. Oversize declared lengths are rejected
before reading; unknown lengths are read through `io.LimitReader(max+1)` and
return HTTP 400 `InvalidRequest`, with no backend request. Rationale: capabilities
must follow administrative effect rather than HTTP verb alone [1].

## 4. Work Breakdown
### Phase A — Authorization capability
- A1. **Edit `internal/config/config.go`:** add `BucketPermissionManage`, accept
  it in credential validation, cloning, environment/file parsing, and comments.
- A2. **Edit `internal/api/authorization.go`:** add
  `authorizationManageBucket`; classify all bucket selector PUT/DELETE routes
  into it and enforce `HasBucketPermission(BucketPermissionManage)`.
- A3. **Edit `internal/api/credential_store.go`:** preserve the new grant through
  snapshot compilation and lookup; no implication from `CanWrite`.
- A4. **Edit `internal/api/authorization_test.go` and
  `internal/api/credential_store_test.go`:** add a table covering every route,
  denial for bare `rw`, acceptance for `manage`, scope denial, and independence
  from create/delete.

### Phase B — Bounded request forwarding
- B1. **Edit `internal/api/utils.go`:** reject `Content-Length` above the limit
  before reads and preserve the existing bounded unknown-length path; return one
  opaque S3 error and never call `forwardToBackend` on excess.
- B2. **Edit `internal/api/handlers.go`:** route all 13 raw bucket configuration
  PUT handlers through `handlePassthroughWithBodyLimit` using 1 MiB. Keep Object
  Lock on its dedicated 100 KiB handler.
- B3. **Edit `internal/api/utils_bucket_management_test.go`:** add
  `TestBucketConfigurationPassthrough_DeclaredAndStreamingBodyLimits` and
  `TestBucketConfigurationPassthrough_OversizeNeverContactsBackend`.

### Phase C — Configuration and documentation
- C1. **Edit `config.yaml.example`, Helm values/schema/deployment tests, and
  credential-file examples:** allow `manage` and explain its independence.
- C2. **Edit `README.md`, `docs/S3_API_IMPLEMENTATION.md`, `SECURITY.md`, and
  `CHANGELOG.md`:** publish the authorization matrix and breaking permission change.
- C3. **Add `test/conformance/bucket_configuration_authorization_test.go`:**
  capability-gated denial and allowed policy/lifecycle round trips without

## 7. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| Existing `rw` clients lose bucket-admin access | Treat as intentional security breaking change; document migration to `manage`. |
| A route remains classified as ordinary write | Maintain one exhaustive registered-route table and assert operation names/selectors in tests. |
| `manage` bypasses bucket scope | Preserve scope check before operation-specific grants and add wildcard/exact/proxied tests. |
| Legitimate provider XML exceeds cap | Use a documented 1 MiB cap, stricter Object Lock limit, and reject before backend contact. |
| Empty DELETE requests are accidentally blocked | Apply body limits without requiring a body and cover all DELETE routes. |
