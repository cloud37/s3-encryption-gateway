## 1. Context & Current State

SigV4 header authentication constructs the canonical request before comparing
the supplied and calculated signatures (`internal/api/auth.go:244-281`). For a
non-presigned request, `createCanonicalRequest` copies the client-provided
`X-Amz-Content-Sha256` value into the payload-hash field
(`internal/api/auth.go:565-580`). A lowercase 64-character hexadecimal value is
accepted as a non-streaming payload mode (`internal/api/auth.go:41-58`), but
`ValidateSignatureV4` returns its signing context without hashing `r.Body`
(`internal/api/auth.go:301-311`). The signature therefore authenticates the
claim, not the bytes received by the gateway. This violates the SigV4 signed-
payload contract, in which `HashedPayload` is SHA-256 over the request payload
[1].

The authenticated request then reaches downstream code unchanged
(`internal/api/auth_middleware.go:132-185`). Only AWS-chunked modes are spooled
and verified by PutObject (`internal/api/handlers.go:1867-1881`) and UploadPart
(`internal/api/handlers.go:3984-4000`). Other body consumers include Complete
Multipart Upload (`internal/api/handlers.go:4268-4277`), DeleteObjects
(`internal/api/handlers.go:5904-5926`), object-lock mutations
(`internal/api/object_lock.go:187-248,294-346,392-449`), and generic passthrough
operations. The passthrough path reads the modified body, computes a fresh hash,
and signs it with backend credentials (`internal/api/utils.go:163-173,222-239`),
turning tampered client bytes into a valid backend request.

The existing streaming implementation already provides the required bounded-
memory primitive: `verifiedAWSBody` is a seekable, closeable reader
(`internal/api/verified_aws_body.go:14-19`), its temporary file is explicitly
mode `0600` (`internal/api/verified_aws_body.go:106-115`), and every failure path
closes and removes the file before a successful rewind
(`internal/api/verified_aws_body.go:116-143`). The correct trust boundary is
`AuthMiddleware`, after request-signature verification and before
`next.ServeHTTP`, rather than a handler allowlist. This covers current and future
routes before backend access, encryption, cache invalidation, or MPU-state
mutation (`internal/api/auth_middleware.go:155-185`).

`UNSIGNED-PAYLOAD` is intentionally outside this issue: it explicitly declines
payload integrity. Existing AWS-chunked modes remain governed by V1.0-SEC-41
(`docs/issues/v0.12-issues.md:99-119`) and must not be double-spooled. Current
presigned canonicalization always uses `UNSIGNED-PAYLOAD`
(`internal/api/auth.go:566-579`), so this issue verifies only a concrete digest
that actually participated in an accepted canonical request.

## 2. Design Goals & Non-Goals

### Goals

1. **Central fail-closed gate** — verify every authenticated concrete SigV4
   payload before any downstream middleware or route can observe its body.
2. **Exact byte integrity** — incrementally calculate SHA-256 over the complete
   received non-streaming body and compare it in constant time with the digest
   authenticated by the canonical request.
3. **Bounded memory** — spool to a mode-`0600` temporary file rather than
   buffering an object-sized request in memory.
4. **Atomic rejection** — digest mismatch, cancellation, short read, and spool
   I/O failure must prevent backend requests, encryption work, cache updates,
   and MPU-state mutation.
5. **Replayable verified body** — downstream consumers receive the exact
   verified bytes from offset zero with an accurate content length.
6. **Protocol separation** — preserve `UNSIGNED-PAYLOAD` and V1.0-SEC-41
   AWS-chunked behavior without ordinary-payload verification or double reads.
7. **Secret-safe failures** — never include expected or calculated digests in
   client errors, logs, metrics, or audit metadata.

### Non-Goals

1. **No integrity promise for `UNSIGNED-PAYLOAD`** — that literal is an explicit
   SigV4 protocol choice and changing it would reject compatible clients.
2. **No second AWS-chunked verifier** — chunk chains, trailers, framing, and
   decoded lengths remain owned by V1.0-SEC-41.
3. **No request-size policy** — this change uses bounded memory but does not add
   a new upload-size or temporary-disk quota; operational limits are separate.
4. **No handler-by-handler verification** — route-specific checks are excluded
   because they are incomplete by construction and unsafe for future routes.
5. **No presigned signed-payload extension** — current presigned requests
   canonicalize `UNSIGNED-PAYLOAD`; supporting a concrete presigned payload is a
   distinct compatibility change.

## 3. Target Interface / Semantics / Behaviour

### Authenticated payload state

```go
type V4SigningContext struct {
    timestamp           string
    credentialScope     string
    signingKey          []byte
    seedSignature       [sha256.Size]byte
    mode                streamingPayloadMode
    expectedPayloadHash [sha256.Size]byte
    verifyPayload       bool
    closed              bool
    closeMu             sync.Mutex
}
```

For header-authenticated SigV4, `ValidateSignatureV4` decodes an accepted
lowercase 64-hex payload hash into `expectedPayloadHash` and sets
`verifyPayload=true`. It does so only after the canonical signature succeeds.
`UNSIGNED-PAYLOAD`, all `STREAMING-*` literals, and current presigned requests
leave `verifyPayload=false`. `Close` zeroizes `signingKey`, `seedSignature`, and
`expectedPayloadHash`, and remains nil-safe and idempotent.

Rationale: retaining parsed bytes in the request-scoped signing context proves
that the expected digest is the value authenticated by the accepted canonical
request; downstream code must not re-read an unauthenticated header.

### Verification and spool contract

```go
func verifyAndSpoolV4Payload(
    r *http.Request,
    signing *V4SigningContext,
) (verifiedAWSBody, error)
```

The helper has these invariants:

1. A nil request, nil context, or `verifyPayload=false` is a programmer error at
   its direct call boundary; middleware calls it only when verification is set.
2. It creates one mode-`0600` temporary file using the existing injectable spool
   operations, streams `r.Body` through `io.MultiWriter(file, sha256.New())`, and
   checks `r.Context()` cancellation while copying.
3. It closes the original request body after the complete copy attempt.
4. It compares the calculated and expected 32-byte values with `hmac.Equal`.
5. On mismatch it closes/removes the temporary file and returns
   `ErrSignatureMismatch`; no digest value appears in the wrapped error.
6. On cancellation it cleans up and returns `ErrStreamingCanceled`; on create,
   chmod, read, write, or seek failure it cleans up and returns
   `ErrStreamingSpool` (renaming these existing sentinels is not required).
7. On success it rewinds to offset zero and returns a `verifiedAWSBody` whose
   `DecodedLength()` is the exact received length.

Rationale: the existing disk-spool type already has tested cleanup and
idempotent ownership semantics (`internal/api/verified_aws_body.go:41-66`). A
shared primitive minimizes new security-sensitive lifecycle code.

### Middleware behavior

After `ValidateSignatureV4` succeeds and before context/credential attachment,
`AuthMiddleware` applies this matrix:

| Accepted SigV4 payload form | Middleware action | Downstream body |
|---|---|---|
| Concrete lowercase SHA-256 | Fully spool, hash, compare, rewind | Verified temporary file |
| `UNSIGNED-PAYLOAD` | Do not pre-read | Original body |
| `STREAMING-*` | Do not pre-read; handler uses V1.0-SEC-41 | Original AWS-chunked body |
| Current presigned request | Do not pre-read | Original body |

On concrete-payload success, middleware assigns the spool to `r.Body`, sets
`r.ContentLength` and `Content-Length` to `DecodedLength()`, defers spool cleanup
until `next.ServeHTTP` returns, and then dispatches. On failure it does not call
`next`; digest mismatch maps to HTTP 403 `SignatureDoesNotMatch`, cancellation
maps to HTTP 400 `IncompleteBody`, and spool I/O maps to opaque HTTP 500
`InternalError` using `writeStreamingPayloadError`
(`internal/api/errors.go:17-35`).

Rationale: middleware is the only common boundary before all routes. It makes
the security property independent of whether a handler encrypts, parses XML,
uses the SDK, or re-signs a passthrough request.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Large signed uploads consume temporary disk before processing | Stream with fixed-size buffers, remove files on every path, document the preflight requirement, and preserve bounded heap use. |
| Middleware replacement loses or truncates the body | Rewind before publication, set exact length fields, and assert byte-for-byte replay including empty and binary bodies. |
| A mismatch reaches a side-effecting handler | Place the gate before `next.ServeHTTP` and prove zero calls/state changes across direct, passthrough, MPU, and object-lock paths. |
| Ordinary verification double-spools AWS-chunked requests | Select it only from the authenticated `verifyPayload` flag; streaming literals retain `verifyPayload=false`. |
| `UNSIGNED-PAYLOAD` clients regress | Do not pre-read that mode and add a reader-observation regression test. |
| Temporary files survive errors or panics | Use idempotent deferred close/remove ownership in middleware and failure-injection tests for create, chmod, read, write, seek, cancellation, and downstream return. |
| Digest material leaks through diagnostics | Return only existing sentinels and assert neither expected nor calculated hash appears in XML, logs, or audit metadata. |
| Presigned requests gain an unauthenticated digest check | Derive `verifyPayload` only when the concrete digest was part of the canonical request; current presigned requests remain unsigned. |

## 8. Definition of Done

- [x] Per `docs/issues/v1.0-issues.md:212-242`, every header-authenticated
      concrete SigV4 payload is fully hashed before downstream dispatch.
- [x] Digest mismatch returns HTTP 403 `SignatureDoesNotMatch` and no expected or
      calculated digest appears in client errors, logs, metrics, or audit data.
- [x] Mismatch tests prove zero backend, encryption, cache, manifest, and MPU-
      state mutation for representative direct and passthrough operations.
- [x] Verified bodies replay byte-for-byte from offset zero with exact
      `ContentLength` and `Content-Length` values.
- [x] Spool files use mode `0600` and are removed after success, mismatch,
      cancellation, every injected I/O failure, and downstream return.
- [x] `UNSIGNED-PAYLOAD`, current presigned requests, and all V1.0-SEC-41
      streaming modes preserve their existing behavior without double spooling.
- [x] `V4SigningContext.Close` zeroizes the expected digest and remains
      idempotent under the race detector.
- [x] New security-critical code in `internal/api` has at least 85% statement
      coverage through the named tests.

      with capability `0`, `CapMultipartUpload`, `CapBatchDelete`, or

## 10. Follow-ups / Out-of-scope items surfaced during planning

1. Add an operator-configurable temporary-spool capacity policy and readiness
   signal if deployment experience shows disk exhaustion requires a separate
   resource-control issue.
2. Evaluate concrete payload hashes for SigV4 presigned requests only after the
   canonical-request implementation explicitly supports and authenticates that
   mode.
3. Consider renaming streaming-specific spool symbols to payload-neutral names
   in a maintenance-only refactor after SEC-43, without combining that churn
   with the security fix.
