## 1. Context & Current State

The persisted chunk format documents `MinChunkSize` as 16 KiB and
`MaxChunkSize` as 1 MiB (`internal/crypto/chunked.go:27-30`). Encryption clamps
configured values to those bounds (`internal/crypto/chunked.go:136-140`), but
`decodeManifest` only base64-decodes and unmarshals backend metadata
(`internal/crypto/chunked.go:529-540`). The manifest is not trusted until its
ciphertext is authenticated.

`newChunkedDecryptReaderForVersion` validates the manifest version and base IV
but copies `manifest.ChunkSize` directly into the reader
(`internal/crypto/chunked.go:345-366`). Its first `Read` allocates
`make([]byte, r.chunkSize+tagSize)` (`internal/crypto/chunked.go:394`) before an
AEAD tag or v2 terminal can authenticate the object. The shared
`validateChunkSize` helper checks only positivity and integer overflow
(`internal/crypto/range_optimization.go:19-26`), so range/preflight arithmetic
also accepts non-canonical chunk sizes. A backend writer can therefore turn a
GET into a large allocation or panic attempt before authentication. The fix is
to make one canonical validator enforce the wire-format bounds and invoke it at
all manifest-derived entry points before arithmetic, allocation, or source I/O.

## 2. Design Goals & Non-Goals

### Goals
1. **Pre-allocation rejection** — reject invalid manifest chunk sizes before any record-sized allocation or source read.
2. **Single invariant** — one validator enforces 16 KiB through 1 MiB inclusive for decrypt and range paths.
3. **Format compatibility** — valid v1/v2 objects at both boundaries remain readable.
4. **Opaque failure** — malformed metadata produces the existing invalid-encryption-metadata response without exposing backend values.
5. **Arithmetic safety** — retain overflow checks even though the format maximum is far below `math.MaxInt`.

### Non-Goals
1. Changing encryption-side clamping; this issue hardens untrusted persisted input.
2. Changing chunk framing, manifest JSON, AEAD, or object-binding semantics.
3. Repairing malformed objects automatically; they must fail closed.

## 3. Target Interface / Semantics / Behaviour

```go
func validateChunkSize(chunkSize int) error

// Invariants: accepts only MinChunkSize <= chunkSize <= MaxChunkSize;
// performs no allocation or I/O; returns an error that does not wrap raw
// metadata or cryptographic material.
```

`newChunkedDecryptReaderForVersion` must call this helper after nil/version
checks and before base-IV decoding or reader construction. Every exported size
and range helper continues to call the same validator. `decodeManifest` remains
a syntax decoder so callers that decode for diagnostics do not accidentally
create a second validation policy; semantic consumers own validation.

| `ChunkSize` | Result |
|---|---|
| `< 16 KiB`, including negative and zero | reject |
| `16 KiB` through `1 MiB` | accept |
| `> 1 MiB`, including overflow-adjacent integers | reject |

Rationale: validating at the semantic constructor makes malformed states
unrepresentable to the allocation-bearing reader while reuse in range helpers
keeps every metadata path consistent [1].

## 4. Work Breakdown

### Phase A — Canonical validation
- A1. **Edit `internal/crypto/range_optimization.go`:** strengthen
  `validateChunkSize(int) error` to enforce `MinChunkSize` and `MaxChunkSize`
  inclusively while retaining the `math.MaxInt-tagSize` guard.
- A2. **Edit `internal/crypto/chunked.go`:** call `validateChunkSize` in
  `newChunkedDecryptReaderForVersion` before decoding the IV or constructing
  `chunkedDecryptReader`.

### Phase B — Regression coverage
- B1. **Edit `internal/crypto/chunked_test.go`:** add
  `TestNewChunkedDecryptReader_RejectsOutOfRangeManifestChunkSizeBeforeRead`
  and `TestNewChunkedDecryptReader_AcceptsManifestChunkSizeBounds`.
- B2. **Edit `internal/crypto/range_optimization_test.go`:** add
  `TestValidateChunkSize_EnforcesFormatBounds` and verify every public size/range
  helper rejects out-of-range values.
- B3. **Edit `internal/crypto/fuzz_test.go`:** add
  `FuzzChunkManifestChunkSizeValidation`; the property is that only the closed
  format interval reaches reader construction and no input panics.
- B4. **Edit `internal/api/handlers_test.go`:** add
  `TestGetObject_InvalidManifestChunkSizeFailsBeforeCiphertextRead`, using a
  counting reader to prove zero backend-body reads after metadata classification.

> Phase B depends on the canonical validator from Phase A.

### Phase C — Documentation and tracking
- C1. **Edit `SECURITY.md`:** document that chunk-manifest resource parameters are validated before allocation and authentication work.
- C2. **Edit `CHANGELOG.md`:** add the SEC-45 availability hardening under Unreleased Security.
- C3. **Edit `docs/issues/v1.0-issues.md`:** mark SEC-45 complete only after independent verification.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Historical objects used non-canonical chunk sizes | The writer has always clamped to the documented interval; test both legal boundaries and call out malformed-object rejection. |
| One manifest path bypasses validation | Reuse the validator in all exported arithmetic helpers and assert the HTTP full-GET path before reads. |
| Validation happens after allocation | Counting-reader and direct-constructor tests require rejection before `Read`. |
| Error details leak attacker metadata | Return the existing opaque invalid-encryption-metadata surface and test the response body. |
