# V1.0-SEC-48 — Recover Identical Multipart Part Reservations Safely — Implementation Plan

Status: Draft
Owner: Security / API / MPU
Priority: P1
Labels: `milestone:v1.0`, `area:security`, `area:api`, `area:mpu`, `area:reliability`

> Scope clarified relative to the tracker entry at
> `docs/issues/v1.0-issues.md`. This plan adds bounded recovery without relaxing
> the immutable plaintext claim introduced by V1.0-SEC-38.

---

## 1. Context & Current State

V1.0-SEC-38 reserves an HMAC plaintext claim before encryption. The Lua script
returns `ErrPartInProgress` whenever an identical claim is already `reserved`
(`internal/mpu/state.go:200-223,772-835`). UploadPart deliberately stops owning
the reservation as soon as the backend call starts because an error may hide a
successful backend commit (`internal/api/handlers.go:4163-4178`). UploadPartCopy
does the same (`internal/api/upload_part_copy.go:1021-1027`). This correctly
prevents a changed plaintext from reusing deterministic nonces, but no later
operation can acquire that reservation; retries receive HTTP 409 until the
entire upload's TTL expires or the client aborts.

Blindly calling `ReleasePart` on every backend error is unsafe: a timeout can
occur after S3 accepted ciphertext, and release would permit different content
to reuse the same `(uploadID, partNumber, chunk)` nonce schedule. Instead,
reserved records need a bounded lease. The same HMAC claim may replace the token
after lease expiry because it produces byte-identical ciphertext; a different
claim remains rejected forever. Token fencing ensures an old worker cannot
commit or release after ownership transfers. Redis server time, not gateway
wall clocks, determines expiry across replicas.

## 2. Design Goals & Non-Goals
### Goals
1. **Nonce safety** — changed plaintext never acquires a reserved or committed part number.
2. **Bounded recovery** — identical retries can proceed after a configurable lease interval.
3. **Fenced ownership** — only the current token can commit, renew, or release.
4. **Replica consistency** — lease decisions use Valkey `TIME` atomically inside Lua.
5. **Path parity** — UploadPart and UploadPartCopy share behavior, metrics, and errors.
6. **Ambiguity preservation** — backend errors do not trigger immediate release.

### Non-Goals
1. Determining whether an ambiguous backend request committed; retries overwrite with identical ciphertext.
2. Allowing changed part replacement for encrypted MPUs.
3. Changing completed manifests or deterministic nonce derivation.
4. Providing fairness among identical concurrent retries.

## 3. Target Interface / Semantics / Behaviour

```go
type PartClaim struct {
    // existing fields...
    LeaseUntilUnixMilli int64 `json:"lease_until_ms,omitempty"`
}

type StateStore interface {
    // existing methods...
    RenewPart(ctx context.Context, uploadID string, partNumber int32, token string) error
}
```

Configuration:
```yaml
multipart_state:
  reservation_lease: 2m
```
Environment: `MPU_RESERVATION_LEASE`; valid range 10 seconds through 15 minutes,
default 2 minutes. `ReservePart` passes lease milliseconds to Lua. Lua obtains
`TIME`, and for an existing record applies:

| Existing state | Incoming claim | Lease | Result |
|---|---|---|---|
| committed | same | N/A | `AlreadyDone` + ETag |
| committed/reserved | different | any | `ErrPartContentMismatch` |
| reserved | same | active | `ErrPartInProgress` |
| reserved | same | expired | atomically replace token/lease, increment revision, return reservation |

`RenewPart` extends only a matching reserved token. Handlers renew around long
local preparation where needed, but never release after backend invocation.
Commit/release scripts already compare tokens and must continue to reject stale
owners. Rationale: leases restore liveness while immutable claims and fencing
retain safety under delayed workers [1].

## 4. Work Breakdown
### Phase A — Lease-aware atomic state protocol
- A1. **Edit `internal/config/config.go`:** add and validate
  `MultipartStateConfig.ReservationLease` with the stated default/range and env.
- A2. **Edit `internal/mpu/state.go`:** add lease data, extend `reservePartScript`
  to use Redis `TIME`, add token-fenced `renewPartScript`/`RenewPart`, and include
  lease values in state decoding without changing committed record semantics.
- A3. **Edit `internal/mpu/state_test.go` and
  `internal/mpu/state_error_paths_test.go`:** add deterministic miniredis clock
  tests for active lease, expiry takeover, changed-claim rejection, stale-token
  commit/release/renew rejection, and concurrent takeover.

### Phase B — Handler recovery semantics
- B1. **Edit `internal/api/handlers.go`:** preserve reservations after any
  backend invocation; map active identical leases to the current 409 response;
  allow an expired identical lease to continue normally. Renew before backend
  invocation if local buffering/encryption consumed a material fraction of the
  lease.
- B2. **Edit `internal/api/upload_part_copy.go`:** use the same renew and
  ownership rules for encrypted destinations.
- B3. **Edit `internal/api/encrypted_mpu_handler_test.go` and
  `internal/api/upload_part_copy_strategy_test.go`:** inject ambiguous backend
  errors, advance store time, retry identical content successfully, and prove
  changed content is still rejected before destination encryption/mutation.

> Phase B depends on the token-fenced lease protocol from Phase A.

### Phase C — Observability and docs
- C1. **Edit `internal/metrics/metrics.go`:** add claim results
  `lease_active`, `lease_reacquired`, and `lease_renewed` to the existing bounded
  label set; do not add upload IDs or part numbers as labels.
- C2. **Edit `config.yaml.example` and Helm values/schema/deployment/tests:**
  expose duration configuration and bounds.
- C3. **Edit `docs/plans/V1.0-SEC-38-plan.md` and
  `docs/adr/0009-encrypted-multipart-uploads.md`:** amend the reservation
  lifecycle and ambiguous-backend recovery contract.
- C4. **Edit `README.md`, `SECURITY.md`, `CHANGELOG.md`, and
  `docs/issues/v1.0-issues.md`:** document retry timing and close after verification.

## 7. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| Lease expires while original backend call is still active | Only identical claims can take over; ciphertext is deterministic and stale commits are token-fenced. |
| Replica clock skew causes early takeover | Use Valkey `TIME` inside the atomic script. |
| Stale owner overwrites current state | Commit, release, and renew all require current token and revision. |
| Lease too short causes duplicate backend traffic | Conservative 2-minute default, bounded configurable range, and renewal before network start. |
| Lease too long preserves poor availability | Maximum 15 minutes and metrics expose active/reacquired outcomes. |

## 8. Definition of Done
- [x] Per `docs/issues/v1.0-issues.md`, identical retries recover after the bounded lease.
- [x] Different plaintext is rejected regardless of lease age.
- [x] Lease takeover, renew, commit, and release are atomic and token-fenced.
- [x] Valkey server time is the sole lease clock.
- [x] No backend error path blindly releases a post-invocation reservation.
- [x] UploadPart and UploadPartCopy have matching behavior and metrics.
- [x] Concurrency/race tests prove one takeover winner and stale-owner rejection.
- [x] Configuration defaults/ranges and Helm rendering are tested and documented.
