## 1. Context & Current State

Object metadata controls password-key derivation on decrypt. The wire parser
accepts every PBKDF2 iteration count at or above 100,000 and places no upper
bound on it (`internal/crypto/kdf.go:65-80`). Argon2id parsing rejects zero
memory, but accepts time zero and any memory value representable by `uint32`;
threads are only constrained by parsing into `uint8` (`internal/crypto/kdf.go:81-111`).
The existing `MaxPBKDF2Iterations = 2,000,000` is applied only while detecting
password-key-manager v1 envelopes (`internal/crypto/kdf.go:22-30`,
`internal/crypto/password_keymanager.go:251-265`), not to object metadata or
password-key-manager v2 envelopes. Consequently, backend-controlled metadata
can request excessive CPU work or an Argon2id allocation before authentication
of the encrypted object.

The allocation/work sinks do not independently enforce a bound. The engine
passes parsed metadata directly to PBKDF2 or Argon2id
(`internal/crypto/engine.go:294-311`), and the non-FIPS Argon2 implementation
calls `argon2.IDKey` after checking only that memory is non-zero
(`internal/crypto/kdf_argon2_default.go:17-23`). Four decrypt paths parse and
derive from metadata (`internal/crypto/engine.go:765-772`,
`internal/crypto/engine.go:1366-1373`, `internal/crypto/engine.go:1607-1614`,
`internal/crypto/engine.go:1878-1886`). Password-key-manager v2 unwrap parses
PBKDF2 or Argon2 parameters and passes them directly to derivation
(`internal/crypto/password_keymanager.go:302-344`), so that envelope is a
second untrusted cost-control surface.

Configuration validates only lower bounds: PBKDF2 must be at least 100,000,
and selected Argon2id write parameters require non-zero time, memory, and
threads (`internal/config/config.go:1944-1974`). Defaults are PBKDF2 600,000 and
Argon2id `time=2`, `memory=19,456 KiB`, `threads=1`
(`internal/config/config.go:894-903`). The current environment loader silently
ignores some malformed or too-small values and has no decrypt-limit settings
(`internal/config/config.go:1128-1155`). Engine and password-key-manager write
options likewise accept or clamp values without establishing that all emitted
costs are supported on decrypt (`internal/crypto/engine_options.go:18-49`,
`internal/crypto/password_keymanager_options.go:9-49`).

The normal XML GET path already maps decryption failures to HTTP 500
`InternalError` (`internal/api/handlers.go:1342-1361`). However, the generic
forwarding path changes any non-policy decryption failure into passthrough and
returns the backend ciphertext (`internal/api/handlers.go:624-645`). The
objective is to reject invalid or operationally excessive KDF parameters before
allocation or expensive work, preserve the S3 XML error surface, and prevent
any KDF-limit rejection from becoming a ciphertext response. This follows the
principle that externally supplied work factors require explicit resource
ceilings [1][2].

## 2. Design Goals & Non-Goals

### Goals

1. **Hard wire bounds** — accept PBKDF2 only in `[100000, 2000000]` and
   Argon2id only with time `[1,10]`, memory `[1,1048576]` KiB, and threads
   `[1,255]`; reject all other values before KDF work.
2. **Operational decrypt bounds** — add operator-configurable maxima with
   defaults of PBKDF2 2,000,000 iterations and Argon2id time 10, memory 65,536
   KiB, and threads 255.
3. **Defense in depth** — enforce hard bounds in metadata/envelope parsers and
   enforce hard plus operational bounds again at every PBKDF2/Argon2 derivation
   sink before allocation or CPU work.
4. **Complete surface coverage** — apply the same contract to all object
   decrypt variants and password-key-manager v2 unwraps, while retaining v1
   and no-prefix envelope compatibility within the PBKDF2 hard maximum.
5. **Write/read consistency** — reject startup/configuration when any KDF
   parameter used for new writes exceeds the deployment's decrypt support.
6. **Typed classification** — make invalid wire parameters distinguishable as
   `*ErrInvalidKDFParams` and valid-but-disallowed costs as
   `*ErrKDFCostTooHigh` through `errors.As` across wrapping layers.
7. **Fail-closed responses** — never return encrypted backend bytes after a
   KDF-parameter or KDF-cost error; S3-facing responses remain generic XML 500
   `InternalError` without exposing parameter details.
8. **Operable rollout** — document inventory, migration, limit increases, and
   coordinated rollout for existing objects or v2 envelopes above new
   operational limits.

### Non-Goals

1. **Wire-format changes** — metadata strings and password-key-manager v1/v2
   envelope layouts remain unchanged; changing them would require a separate
   compatibility design.
2. **Raising write defaults** — PBKDF2 600,000 and Argon2id `2/19456/1` remain
   write defaults; this issue bounds attacker-controlled decrypt cost rather
   than retuning password-hardening policy.
3. **Automatic fallback or clamping on decrypt** — an encoded cost is never
   reduced because deriving with different parameters cannot authenticate the
   ciphertext and would hide corruption or incompatibility.
4. **Automatic object rewriting** — migration remains an operator-controlled
   GET-through-gateway then PUT-through-gateway operation because rewriting
   stored ciphertext requires authorization and a maintenance window.
5. **Argon2 admission control by default** — a process-wide concurrency gate is
   deferred unless representative load tests show that the 65,536 KiB default
   per-derivation ceiling is insufficient; arbitrary semaphore sizing in this
   0.25-day change would risk request starvation and cancellation leaks.

## 3. Target Interface / Semantics / Behaviour

### Hard and operational contracts

| Algorithm / parameter | Hard wire-valid range | Default operational decrypt maximum | Write-side rule |
|---|---:|---:|---|
| PBKDF2-SHA256 iterations | 100,000..2,000,000 | 2,000,000 | `iterations <= decrypt_limits.pbkdf2.max_iterations` |
| Argon2id time | 1..10 | 10 | `time <= decrypt_limits.argon2id.max_time` |
| Argon2id memory (KiB) | 1..1,048,576 | 65,536 | `memory <= decrypt_limits.argon2id.max_memory` |
| Argon2id threads | 1..255 | 255 | `threads <= decrypt_limits.argon2id.max_threads` |

Hard bounds define what this release can safely parse and preserve the existing
wire field widths. Operational maxima let operators set a lower resource
budget without declaring otherwise well-formed data corrupt. Bounds are
inclusive. Missing `MetaKDFParams` remains legacy PBKDF2 at 100,000 iterations
(`internal/crypto/kdf.go:55-58`) and therefore passes the default and every
valid configurable PBKDF2 maximum.

Add the following crypto contract to `internal/crypto/kdf.go`:

```go
const (
	MaxPBKDF2Iterations = 2_000_000
	MinArgon2idTime      = uint32(1)
	MaxArgon2idTime      = uint32(10)
	MinArgon2idMemory    = uint32(1)
	MaxArgon2idMemory    = uint32(1_048_576) // KiB; wire-compatibility ceiling
	MinArgon2idThreads   = uint8(1)
	MaxArgon2idThreads   = uint8(255)
)

type KDFLimits struct {
	PBKDF2MaxIterations int
	Argon2idMaxTime      uint32
	Argon2idMaxMemory    uint32
	Argon2idMaxThreads   uint8
}

func DefaultKDFLimits() KDFLimits
func ValidateKDFParams(params KDFParams, limits KDFLimits) error
```

`ParseKDFParams` must validate all hard ranges before returning. The shared
`ValidateKDFParams` must first repeat hard validation, then compare against
operational maxima. `engine.deriveKeyWithParams` and
`passwordKeyManager.deriveUnwrapKey` must call it immediately before selecting
PBKDF2 or Argon2id. This deliberate parser-plus-sink duplication prevents a
future caller that constructs `KDFParams` directly from bypassing the safety
contract [3].

### Typed errors

```go
type ErrInvalidKDFParams struct {
	Algorithm KDFAlgorithm
	Parameter string
	Value     uint64
	Reason    string
}

func (e *ErrInvalidKDFParams) Error() string

type ErrKDFCostTooHigh struct {
	Algorithm KDFAlgorithm
	Parameter string
	Requested uint64
	Maximum   uint64
}

func (e *ErrKDFCostTooHigh) Error() string
```

Malformed syntax, unsupported algorithms, and values outside hard wire ranges
return `*ErrInvalidKDFParams`. Values inside hard ranges but above configured
operational maxima return `*ErrKDFCostTooHigh`. Callers wrap with `%w`; tests
classify with `errors.As`, not string matching. These are types rather than
sentinel values because the algorithm/parameter/value fields are required for
safe internal diagnostics while S3 clients receive only the canonical generic
message [4].

### Configuration contract

The exact application YAML shape is:

```yaml
encryption:
  kdf:
    algorithm: "pbkdf2-sha256"
    pbkdf2:
      iterations: 600000
    argon2id:
      time: 2
      memory: 19456
      threads: 1
    decrypt_limits:
      pbkdf2:
        max_iterations: 2000000
      argon2id:
        max_time: 10
        max_memory: 65536 # KiB
        max_threads: 255
```

Add these exact config types and environment bindings:

```go
type KDFDecryptLimitsConfig struct {
	PBKDF2  PBKDF2DecryptLimitsConfig  `yaml:"pbkdf2"`
	Argon2id Argon2idDecryptLimitsConfig `yaml:"argon2id"`
}

type PBKDF2DecryptLimitsConfig struct {
	MaxIterations int `yaml:"max_iterations" env:"ENCRYPTION_KDF_DECRYPT_LIMITS_PBKDF2_MAX_ITERATIONS"`
}

type Argon2idDecryptLimitsConfig struct {
	MaxTime    uint32 `yaml:"max_time" env:"ENCRYPTION_KDF_DECRYPT_LIMITS_ARGON2ID_MAX_TIME"`
	MaxMemory  uint32 `yaml:"max_memory" env:"ENCRYPTION_KDF_DECRYPT_LIMITS_ARGON2ID_MAX_MEMORY"`
	MaxThreads uint8  `yaml:"max_threads" env:"ENCRYPTION_KDF_DECRYPT_LIMITS_ARGON2ID_MAX_THREADS"`
}
```

`KDFConfig` gains this field:

```go
DecryptLimits KDFDecryptLimitsConfig `yaml:"decrypt_limits"`
```

`LoadConfig` defaults all four values exactly as in
the table, and environment overrides use the exact names shown in the tags.
Present but malformed environment values must make `LoadConfig` fail rather
than silently retain defaults. `Config.Validate` enforces each operational
maximum within its hard range and enforces all configured write parameters at
or below the corresponding decrypt maximum, regardless of the currently
selected write algorithm; this prevents a later algorithm switch from
activating an unsupported write configuration.

The exact Helm values shape mirrors the application's hierarchy using chart
camelCase and the existing `configValue` wrapper:

```yaml
config:
  encryption:
    kdf:
      decryptLimits:
        pbkdf2:
          maxIterations:
            value: "2000000"
            valueFrom: {}
        argon2id:
          maxTime:
            value: "10"
            valueFrom: {}
          maxMemory:
            value: "65536"
            valueFrom: {}
          maxThreads:
            value: "255"
            valueFrom: {}
```

The deployment template emits the four corresponding environment variables,
supporting either `value` or `valueFrom`. The schema accepts string or integer
values through the existing wrapper and documents inclusive ranges; runtime
validation remains authoritative.

### Engine and password-key-manager wiring

Add `kdfLimits KDFLimits` to both `engine` and `passwordKeyManager`. Add:

```go
func WithKDFLimits(limits KDFLimits) Option
func WithPasswordKMKDFLimits(limits KDFLimits) PasswordKMOption
```

Constructors initialize `DefaultKDFLimits()` before applying options. Engine
construction validates final write options against final limits and returns an
error rather than silently ignoring or clamping unsupported values. Password
key-manager construction does the same for PBKDF2 and Argon2id options in both
default and FIPS files. `cmd/server/main.go` builds one `crypto.KDFLimits` from
validated config and passes it to the engine and every password key manager,
including the password fallback manager (`cmd/server/main.go:473-520`,
`cmd/server/main.go:580-603`). One value shared by both consumers prevents the
MPU envelope path and ordinary object path from drifting.

For password-key-manager v2, `tryUnwrapV2` validates PBKDF2/Argon2 parameters
after the fixed-length payload check and before slicing salt/nonce or invoking
derivation (`internal/crypto/password_keymanager.go:302-344`). V1 detection
retains its existing `[MinPBKDF2Iterations, MaxPBKDF2Iterations]` format
discriminator, then applies the operational PBKDF2 maximum before work. The
legacy no-prefix envelope remains fixed at 100,000. A recognized v2 marker with
invalid or excessive cost is authoritative and must return its typed error; it
must not fall through to v1/legacy format attempts.

### HTTP behaviour

| Path | Condition | Result |
|---|---|---|
| Normal/ranged GET and MPU manifest decrypt | `ErrInvalidKDFParams` or `ErrKDFCostTooHigh` anywhere in the chain | HTTP 500, S3 XML code `InternalError`, canonical generic message, no response ciphertext |
| Generic forwarded GET | Same typed error from `engine.Decrypt` | Fail closed with HTTP 500 `InternalError`; do not execute the current encrypted-body passthrough branch |
| Other generic forwarded GET decrypt failure | Existing behaviour | Unchanged by this issue |
| Startup | Invalid limits or write cost exceeds decrypt support | Configuration error; process does not begin serving |

`errors.As` checks must occur before the generic forwarding fallback at
`internal/api/handlers.go:629-645`. Existing XML error writing remains the
single client surface; detailed requested/max values are logged internally
with bucket/key and error type, not copied to XML. This keeps compatibility
with existing S3 clients while preventing a fail-open ciphertext response.

### Inventory, migration, and rollout

Before lowering a limit, operators must inventory `MetaKDFParams` using
backend object metadata and `s3eg-cli inspect`, as used by the existing
Argon2id migration procedure (`docs/MIGRATION.md:188-217`). Password-key-manager v2 costs
embedded in encrypted MPU manifests cannot be inventoried from object headers;
operators must retain the old limit until affected MPU objects have been read
and rewritten. `docs/MIGRATION.md` must define a report with bucket, key,
algorithm, requested costs, proposed maxima, and classification
(`within-limit`, `above-operational-limit`, or `invalid-hard-limit`).

Objects above a proposed operational limit are migrated by GET through pods
that still support the old cost, followed by PUT through pods using supported
write parameters (`docs/MIGRATION.md:188-217`). Rollout is coordinated: first
deploy readers whose limits cover the complete inventory and whose write costs
fit the future limits; next rewrite and verify outliers; then lower limits on
all replicas in one maintenance rollout. Mixed replicas with different limits
must not receive traffic during the cutover because availability would depend
on pod selection. Data above a hard limit cannot be read by the new release;
it must be rewritten through the prior trusted release before upgrade. No
temporary production limit may exceed a hard wire bound.

- B1. **Edit `internal/crypto/engine.go`:** store `kdfLimits`, initialize

### Tier 2 conformance

Tier 2 proves the provider-relevant external contract: backend metadata can be
stored and retrieved, but the gateway rejects an excessive cost without
returning plaintext or ciphertext. Internal parser boundaries, typed errors,
allocation hooks, password-key-manager envelope dispatch, config, Helm, and
FIPS behavior remain Tier 1.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Existing objects or MPU v2 envelopes request more than the new 65,536 KiB Argon2 operational default and become unreadable. | Inventory before rollout, temporarily configure a within-hard-bound maximum covering known data, migrate via trusted old readers, verify rewrites, then lower all replicas together. |
| A parser-only check is bypassed by direct construction of `KDFParams`. | Repeat validation in engine, Argon2, and password-key-manager derivation sinks immediately before work. |
| A recognized invalid v2 envelope falls through to legacy detection and performs additional KDF attempts. | Treat the v2 marker as authoritative and return typed validation errors directly. |
| Write configuration emits objects that the same deployment cannot decrypt. | Validate all write parameters against operational decrypt maxima at startup and constructor boundaries. |
| Generic proxy fallback exposes ciphertext when KDF validation fails. | Classify wrapped typed errors before fallback and return canonical XML 500 with zero ciphertext bytes. |
| Mixed replicas have different operational limits during rollout. | Require coordinated rollout/traffic drain in the migration runbook; do not lower limits until inventory and rewrites complete. |
| Helm accepts values that application runtime rejects. | Encode documented ranges in schema descriptions/types, render all exact env names, and retain runtime validation as the authoritative gate. |
| Optional Argon2 semaphore deadlocks or causes unfair starvation. | Do not add it in this change; consider a context-aware weighted admission controller only after measured concurrent-memory evidence, with its own tests and configuration. |
| Tightening PBKDF2 option clamping breaks callers that relied on silent correction. | Return explicit constructor/config errors; update all in-repository callers in the same change and document the deliberate fail-fast behaviour. |

## 10. Follow-ups / Out-of-scope items surfaced during planning

1. **Measured Argon2 admission control** — if load tests demonstrate unsafe
   aggregate memory despite the per-call ceiling, design a context-aware
   process-wide weighted limiter whose weight is requested KiB; define queue
   timeout, fairness, metrics, and shutdown semantics before implementation.
2. **Fleet inventory command** — a dedicated command that aggregates KDF costs
   and emits machine-readable outlier lists could reduce operator effort, but
   is not required for enforcing bounds and does not fit the 0.25-day slice.
3. **Per-bucket decrypt budgets** — global deployment limits are intentional
   for this issue; policy-specific limits would complicate engine caching and
   rollout consistency.
