## 1. Context & Current State

SEC-43 intentionally deferred request-size policy while requiring every
concrete SigV4 payload to be fully hashed before dispatch
(`docs/plans/V1.0-SEC-43-plan.md:81-91`). `AuthMiddleware` performs that spool
before routing (`internal/api/auth_middleware.go:185-207`).
`verifyAndSpoolV4Payload` creates a temporary file and copies until EOF with no
declared-length check or byte cap (`internal/api/verified_aws_body.go:151-206`).
AWS-chunked verification uses the same unmetered temporary-file lifecycle
(`internal/api/verified_aws_body.go:81-148`). An authenticated client can fill
the filesystem with one large request or many concurrent requests before any
handler limit is reached.

Some handlers have narrower semantic limits: UploadPart uses
`Server.MaxPartBuffer` (`internal/api/handlers.go:3842-3849,4141-4155`), CreateBucket
uses 64 KiB (`internal/api/handlers.go:3227`), and Object Lock configuration is
bounded independently. Those checks occur after concrete payload spooling and
therefore cannot protect temporary disk. The fix is a process-wide spool manager
shared by authentication and streaming handlers. It applies operation-aware
single-request limits, reserves declared lengths before file creation, meters
unknown lengths while reading, and atomically caps aggregate in-flight bytes.

## 2. Design Goals & Non-Goals
### Goals
1. **Per-request bounds** — no verified spool exceeds its operation's configured maximum.
2. **Aggregate bound** — concurrent spool files cannot exceed a process-wide byte budget.
3. **Early rejection** — oversized non-negative Content-Length is rejected before file creation/read.
4. **Streaming enforcement** — absent or deceptive lengths are capped while bytes arrive.
5. **Single accounting path** — ordinary concrete SigV4 and AWS-chunked verified bodies use the same manager.
6. **Leak-free release** — all success, error, cancellation, and downstream-return paths release bytes exactly once.
7. **Operational visibility** — bounded metrics expose current bytes and rejection reason without high-cardinality labels.

### Non-Goals
1. Limiting `UNSIGNED-PAYLOAD` bodies that are not spooled at authentication; handler limits remain responsible.
2. Coordinating quotas across replicas; each pod enforces its own filesystem budget.
3. Replacing temporary files with streaming-to-backend, which would violate pre-dispatch payload verification.
4. Managing node-level ephemeral-storage eviction outside the process.

## 3. Target Interface / Semantics / Behaviour

```go
type SpoolManager interface {
    // Acquire reserves declared bytes; n must be >= 0 and <= requestLimit.
    Acquire(ctx context.Context, n, requestLimit int64) (SpoolReservation, error)
}

type SpoolReservation interface {
    Grow(delta int64) error // atomically enforces request and aggregate limits
    Release()               // thread-safe and idempotent
}
```

Sentinels: `ErrSpoolRequestLimit` and `ErrSpoolCapacity`. The implementation uses
atomic/mutex-protected counters; it does not block waiting for capacity. A
verified file owns its reservation and releases it from idempotent `Close`.

```yaml
server:
  spool_directory: ""                 # empty = os.TempDir()
  max_verified_spool_bytes: 5368709120 # 5 GiB single PutObject ceiling
  max_aggregate_spool_bytes: 10737418240 # 10 GiB per process
```

Operation limits are the minimum of the global single-spool ceiling and known
semantic cap: UploadPart uses `max_part_buffer`; bucket configuration uses its
control-plane cap; DeleteObjects/Complete and other XML operations use 1 MiB;
PutObject uses `max_verified_spool_bytes`. Unknown future body-bearing routes
use a conservative 1 MiB default until explicitly classified. Declared excess
maps to HTTP 413 `EntityTooLarge`; aggregate exhaustion maps to HTTP 503
`SlowDown`; malformed/truncated payload integrity retains existing errors.

Rationale: admission control must happen at the resource acquisition boundary,
not after authentication has consumed the scarce resource [1].

## 4. Work Breakdown
### Phase A — Configuration and spool manager
- A1. **Edit `internal/config/config.go`:** add the three server fields, defaults,
  env loading (`SERVER_SPOOL_DIRECTORY`, `SERVER_MAX_VERIFIED_SPOOL_BYTES`,
  `SERVER_MAX_AGGREGATE_SPOOL_BYTES`), validation (positive sizes, aggregate >=
  single), and reload policy (size limits reloadable; directory restart-only).
- A2. **New `internal/api/spool_manager.go`:** implement reservation accounting,
  operation-limit classification from method/path/query, early declared-length
  admission, incremental growth, idempotent release, and sentinels.
- A3. **New `internal/api/spool_manager_test.go`:** add
  `TestSpoolManager_DeclaredLengthAdmission`,
  `TestSpoolManager_UnknownLengthGrowth`,
  `TestSpoolManager_AggregateConcurrentLimit`, and
  `TestSpoolReservation_ReleaseIdempotent`.

### Phase B — Integrate every verified spool
- B1. **Edit `internal/api/verified_aws_body.go`:** accept a manager/reservation
  and request limit in both verification functions; create files in configured
  directory; reserve declared decoded/body length before creation; call `Grow`
  before each write for unknown lengths; transfer reservation ownership to
  `verifiedAWSFile`; clean up/release on every failure.
- B2. **Edit `internal/api/auth_middleware.go`:** accept the shared manager,
  classify limits before concrete-body verification, and map quota sentinels to
  the specified S3 errors before calling `next`.
- B3. **Edit `internal/api/handlers.go`:** pass the same manager and operation
  limit to AWS-chunked PutObject/UploadPart verification; do not double-reserve
  concrete bodies already spooled by middleware.
- B4. **Edit constructors/call sites in `cmd/server/main.go` and
  `test/harness/gateway.go`:** construct exactly one manager per gateway process
  and inject it into middleware/handler; retain a default manager helper for tests.

> Phase B depends on the ownership semantics from Phase A.

### Phase C — Error, metrics, and concurrency proof
- C1. **Edit `internal/api/errors.go`:** map request-limit to 413 `EntityTooLarge`
  and aggregate exhaustion to 503 `SlowDown` without filesystem paths or limits
  in client-visible text.
- C2. **Edit `internal/metrics/metrics.go`:** add
  `s3_gateway_spool_bytes` gauge and
  `s3_gateway_spool_rejections_total{reason}` with bounded reasons
  `request_limit`/`aggregate_limit`.
- C3. **Edit `internal/api/verified_payload_test.go`,
  `aws_chunked_reader_test.go`, and `auth_middleware_test.go`:** test declared,
  unknown, concurrent, cancellation, I/O failure, downstream panic/return, exact
  release, no file leaks, and no downstream invocation.
- C4. **Add `test/conformance/spool_limits_test.go`:** verify valid bounded
  concrete PutObject/UploadPart requests and an oversized signed request rejected
  without object/part mutation.

### Phase D — Operator surfaces and docs
- D1. **Edit `config.yaml.example` and Helm values/schema/deployment/tests:**
  expose limits and optional spool directory; document Kubernetes ephemeral-
  storage sizing as at least aggregate budget plus safety margin.
- D2. **Edit `README.md`, `SECURITY.md`, `docs/DEPLOYMENT.md`, and
  `docs/SCALING.md`:** document operation limits, aggregate semantics, 413/503,
  and multi-replica capacity.
- D3. **Edit `CHANGELOG.md`, `docs/plans/V1.0-SEC-43-plan.md`, and
  `docs/issues/v1.0-issues.md`:** close the deferred SEC-43 quota follow-up and
  mark SEC-49 complete after verification.

## 7. Risks & Mitigations
| Risk | Mitigation |
|---|---|
| Defaults reject previously accepted very large signed uploads | Set PutObject ceiling to S3's 5 GiB single-PUT maximum and document tuning/MPU use. |
| Declared lengths lie | Meter actual bytes and fail before writing bytes that exceed reservation. |
| Accounting leak permanently exhausts capacity | Transfer one reservation owner, make release idempotent, and test every cleanup path plus final zero gauge. |
| Check-then-add races exceed aggregate | Perform admission and growth under one synchronization primitive; stress under `-race`. |
| Aggregate quota blocks healthy requests during bursts | Fail fast with retryable `SlowDown`, expose metrics, and document per-pod sizing/scaling. |
| Middleware and handler double-account | Concrete bodies are owned by middleware; only streaming modes enter handler verification; assert both paths. |
| Spool directory change strands files | Mark directory restart-only and retain close/remove lifecycle in the originating manager. |

## 10. Follow-ups / Out-of-scope items surfaced during planning
1. A node-wide or cluster-wide shared quota would require an external coordinator and is unnecessary when pod ephemeral-storage requests/limits match the per-process budget.
2. Streaming verified bytes directly to backend while preserving pre-mutation integrity would require a transactional backend and is not available in S3.
