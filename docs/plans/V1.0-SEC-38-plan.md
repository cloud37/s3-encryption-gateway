# V1.0-SEC-38 — Prevent Nonce Reuse on Multipart Part Replacement — Implementation Plan

Status: Complete
Owner: Security
Priority: P0

> `docs/issues/v1.0-issues.md`. The tracker summarizes the nonce-reuse hazard;
> this plan expands it into the complete state, API, rollout, and test contract.

## 1. Context & Current State

Encrypted MPU uses one DEK per upload and derives each chunk nonce from the
upload identity, part number, and chunk index
(`docs/adr/0009-encrypted-multipart-uploads.md:85`). This makes distinct part
numbers safe, but makes every encryption of the same `(uploadID, partNumber)`
reuse the same AEAD nonce sequence. That is safe only when the plaintext is
identical. S3 normally permits replacing a part by uploading the same part
number again, so the gateway must narrow that behavior for encrypted MPUs to
preserve the nonce-uniqueness requirement of GCM [1].

The current request path reads encrypted-upload state and immediately calls
`encryptMPUPartWithState` (`internal/api/handlers.go:3869`), which unwraps the
DEK and constructs the deterministic part encryptor
(`internal/api/handlers.go:4375-4392`). It then sends ciphertext to the backend
at `internal/api/handlers.go:3964` and records the part only after that write at
`internal/api/handlers.go:3998-4001`. Consequently, a changed replacement body
is encrypted and written under the same nonce schedule before state can
observe it. The state store's `AppendPart` performs a separate `EXISTS`, then
unconditionally overwrites `part:<N>` with `HSET`
(`internal/mpu/state.go:531-556`); this is neither a pre-encryption claim nor
an atomic compare-and-set.

The durable record contains part number, ETag, lengths, and chunk count but no
content commitment (`internal/mpu/state.go:50-56`). `UploadState` has no schema
version, lifecycle phase, or revision (`internal/mpu/state.go:59-81`). Complete
parses and normalizes the client's selected parts
(`internal/api/handlers.go:3575-3621`, `internal/api/handlers.go:3624-3693`),
but writes a manifest from every state record sorted by part number
(`internal/api/handlers.go:4642-4670`) without first proving that each selected
part and ETag exactly matches a committed claim. It writes that companion
manifest before calling backend Complete (`internal/api/handlers.go:4184-4226`).
The completed manifest schema is already established at
`internal/crypto/mpu_manifest.go:38-67` and must not change.

`UploadPartCopy` has the same gap. Encrypted destinations are selected from
live bucket policy (`internal/api/upload_part_copy.go:311-313`), re-encrypted,
written to the backend, and only then appended to state
(`internal/api/upload_part_copy.go:735-918`). Existing observability counts
generic part and state-store outcomes (`internal/metrics/metrics.go:421-441`,
`internal/metrics/metrics.go:982-1000`) but cannot distinguish new claims,
identical retries, replacement rejections, or legacy-state refusals. The
objective is therefore to immutably claim the first plaintext for each
encrypted `(uploadID, partNumber)` before encryption or destination mutation,
while retaining byte-identical retries and the existing completed-object
format.

## 2. Design Goals & Non-Goals

### Goals

1. **Immutable first-content claim** — the first accepted plaintext for each
   encrypted `(uploadID, partNumber)` is durably identified by an HMAC-SHA256
   commitment keyed by that upload's DEK; no different plaintext reaches
   encryption or destination-backend mutation.
2. **Safe idempotency** — an identical retry is accepted, returns the
   committed ETag when available, and, if recovery requires re-upload, produces
   byte-identical ciphertext under the existing deterministic nonce schedule.
3. **Atomic state transitions** — Valkey `ReservePart`, `CommitPart`, complete,
   and abort transitions use Lua so claim comparison, phase/revision checks,
   field mutation, and TTL refresh are indivisible across gateway replicas [4].
4. **Exact completion** — Complete validates the ordered client-selected part
   set and normalized ETags against committed records and builds the manifest
   from exactly that selected set, not every previously uploaded part.
5. **Operation parity** — ordinary `UploadPart` and `UploadPartCopy` use the
   same claim and commit protocol, S3 error surface, lifecycle rules, and
   metrics.
6. **Fail-closed rollout** — state created by pre-change binaries cannot accept
   UploadPart, UploadPartCopy, or Complete after the new binary is deployed;
   clients receive `OperationAborted` and must Abort then create a new upload.
7. **Format stability** — ciphertext framing, IV derivation, final object
   bytes, companion-manifest schema, and completed-object read behavior remain
   unchanged.

### Non-Goals

1. **Allowing changed encrypted-part replacement** — assigning a fresh nonce
   generation would require a completed-object format change; abort/new upload
   is the required recovery path.
2. **Changing plaintext MPU semantics** — MPUs without encrypted state retain
   normal S3 replacement behavior because no gateway AEAD nonce is involved.
3. **Adding a client-visible checksum protocol** — the commitment is internal
   durable state, not a replacement for S3 checksum headers or ETags.
4. **Migrating in-flight legacy encrypted uploads** — their prior part history
   cannot be reconstructed with trustworthy plaintext commitments, so an
   automatic migration cannot prove nonce safety.
5. **Changing completed objects** — existing and newly completed MPU objects
   continue to use manifest version 1 and the current decryption path.

## 3. Target Interface / Semantics / Behaviour

### 3.1 State-store interface and records

Replace `AppendPart` with reservation and commit operations and add explicit
lifecycle operations:

```go
var (
	ErrPartContentMismatch = errors.New("mpu: part content differs from immutable claim")
	ErrPartInProgress      = errors.New("mpu: part reservation is in progress")
	ErrInvalidStateVersion = errors.New("mpu: unsupported in-flight state version")
	ErrInvalidPhase        = errors.New("mpu: upload is not open")
	ErrRevisionConflict    = errors.New("mpu: state revision changed")
	ErrCompleteMismatch    = errors.New("mpu: selected parts or etags do not match committed state")
)

type UploadPhase string

const (
	UploadPhaseOpen       UploadPhase = "open"
	UploadPhaseCompleting UploadPhase = "completing"
	UploadPhaseCompleted  UploadPhase = "completed"
	UploadPhaseAborting   UploadPhase = "aborting"
	UploadPhaseAborted    UploadPhase = "aborted"
)

type PartStatus string

const (
	PartStatusReserved  PartStatus = "reserved"
	PartStatusCommitted PartStatus = "committed"
)

type PartClaim struct {
	PartNumber int32      `json:"pn"`
	Claim      string     `json:"claim"` // base64url HMAC-SHA256
	PlainLen   int64      `json:"plain_len"`
	Status     PartStatus `json:"status"`
	Token      string     `json:"token"`
	ETag       string     `json:"etag,omitempty"`
	EncLen     int64      `json:"enc_len,omitempty"`
	ChunkCount int32      `json:"chunks,omitempty"`
}

type Reservation struct {
	Token         string
	Revision      uint64
	CommittedETag string
	AlreadyDone   bool
}

type SelectedPart struct {
	PartNumber int32  `json:"pn"`
	ETag       string `json:"etag"`
}

// Invariants: implementations are safe for concurrent replicas; honor ctx;
// never mutate on a failed comparison; treat nil inputs as InvalidArgument;
// make ReservePart/CommitPart idempotent for the same token and claim; and do
// not retain plaintext, DEKs, or caller-owned byte slices.
type StateStore interface {
	Create(ctx context.Context, state *UploadState) error
	Get(ctx context.Context, uploadID string) (*UploadState, error)
	ReservePart(ctx context.Context, uploadID string, part PartClaim) (Reservation, error)
	ReleasePart(ctx context.Context, uploadID string, partNumber int32, token string) error
	CommitPart(ctx context.Context, uploadID string, part PartClaim) error
	BeginComplete(ctx context.Context, uploadID string, selected []SelectedPart) (*UploadState, uint64, error)
	Reopen(ctx context.Context, uploadID string, revision uint64) error
	FinalizeComplete(ctx context.Context, uploadID string, revision uint64) error
	BeginAbort(ctx context.Context, uploadID string) (uint64, error)
	FinalizeAbort(ctx context.Context, uploadID string, revision uint64) error
	Delete(ctx context.Context, uploadID string) error
	List(ctx context.Context) ([]UploadState, error)
	HealthCheck(ctx context.Context) error
	Close() error
}
```

`UploadState` adds `StateVersion uint8` (`2` for this contract),
`Phase UploadPhase`, and monotonic `Revision uint64`. `Create` writes version 2,
phase `open`, revision 1. Part fields remain separate `part:<N>` hash fields so
Lua can compare and update one claim without rewriting encrypted metadata.
The claim is keyed and discloses neither plaintext nor a reusable unkeyed
content hash [2]. The interface is intentionally state-oriented rather than
Valkey-oriented so handler tests can model each transition without Redis
commands.

### 3.2 Content-claim algorithm

For the exact plaintext bytes `P`, compute:

```text
claim = Base64URL-NoPad(HMAC-SHA256(
    DEK,
    "s3eg:mpu-part-claim:v1\x00" ||
    uint32_be(partNumber) ||
    uint64_be(len(P)) ||
    P
))
```

The domain is the exact 23-byte ASCII-plus-NUL string shown above. Integers are
unsigned big-endian; part numbers are restricted to 1..10,000 and lengths to
the existing part-size/buffer limits. Implement `ComputePartClaim` by streaming
the already bounded plaintext through `hmac.New(sha256.New, dek)`, compare
claims with `hmac.Equal`, and zeroize the unwrapped DEK on every exit. HMAC's
domain separation and keyed construction follow RFC 2104 [2]; the commitment
is not stored in the completed manifest.

The handler must acquire the complete plaintext into the existing bounded
seekable body before reservation because content equality cannot be decided
from length or ETag. For ordinary UploadPart, `ReservePart` occurs before
constructing the encryptor and before any S3 client operation. For
UploadPartCopy, source `HEAD`/`GET` and decryption are necessarily content
acquisition; reservation still occurs before destination encryption and before
any destination-backend mutation. No design can compare the plaintext claim
without reading an uncached copy source.

### 3.3 Atomic Valkey protocol

Embed reviewed Lua scripts in `internal/mpu/state.go`; execute each with
`EVALSHA` and transparent `NOSCRIPT` reload. Every script first verifies that
`meta` decodes to state version 2 and the expected phase. Because encrypted
`meta` cannot be inspected by Lua, persist non-secret control fields alongside
it as `state_version`, `phase`, and `revision`; authenticated `meta` mirrors
them, and `Get` rejects disagreement.

`ReservePart` atomically performs this matrix:

| Existing state | Request claim | Result | Mutation |
|---|---|---|---|
| Missing upload | Any | `ErrUploadNotFound` | None |
| Version absent/1 | Any | `ErrInvalidStateVersion` | None |
| Phase not `open` | Any | `ErrInvalidPhase` | None |
| No `part:N` | Any | Return new random 128-bit token and revision | Write immutable claim/length, `reserved`, token; increment revision; refresh TTL |
| `reserved` | Same | `ErrPartInProgress` | None; client may retry after the active request resolves |
| `committed` | Same | `AlreadyDone=true` and exact committed ETag | Refresh TTL only; no encryption/backend I/O |
| Any | Different | `ErrPartContentMismatch` | None |

The random reservation token is generated by Go before the script and is
accepted only for a new claim. `CommitPart` requires version 2, phase `open`,
the exact claim, and the exact reservation token; it atomically changes status
to `committed`, stores canonical backend ETag/length/chunk count, increments
revision, and refreshes TTL. Repeating the same commit is success; any changed
field or token is `ErrRevisionConflict`. A backend failure leaves `reserved`;
the owning request calls a conditional `ReleasePart` operation (included in the
interface implementation even if kept unexported) that deletes only its token's
reservation. Crash-stale reservations expire with the upload TTL; clients must
abort/new-upload rather than bypass a reservation whose owner is unknown.

### 3.4 Complete and lifecycle contract

The legal transition graph is:

```text
Create -> open
open -> completing -> completed -> Delete
open -> aborting -> aborted -> Delete
completing -> open                 (backend Complete failed)
aborting -> open                   (backend Abort failed)
```

`BeginComplete` is one Lua operation. It requires version 2 and phase `open`;
requires 1..10,000 strictly ascending, unique selected parts; requires every
selected part to exist with status `committed`; and compares every normalized,
quoted ETag exactly. Uploaded but unselected committed parts are legal under S3
semantics and are omitted. Any reserved part named by the request is rejected.
On success, it sets `completing`, increments revision, and returns a state
snapshot containing exactly the selected records in request order. The handler
builds the unchanged version-1 manifest from that snapshot, writes the existing
companion object, and passes the same selected list to backend Complete.

Backend Complete success is followed by conditional `FinalizeComplete`; a
failure uses conditional `Reopen`. Both require the revision returned by
`BeginComplete`, preventing stale requests from changing a newer lifecycle.
Abort uses the corresponding `BeginAbort`/`FinalizeAbort` pair. Only Abort is
accepted for legacy state. UploadPart, UploadPartCopy, and Complete against a
missing-version/version-1 encrypted state return the error below; ListParts may
remain read-only. Existing completed objects never consult this state version.

### 3.5 HTTP behavior

| Condition | S3 code | HTTP | Message / behavior |
|---|---:|---:|---|
| First content successfully reserved and committed | Success | 200 | Return backend ETag |
| Identical retry after commit | Success | 200 | Return the exact stored ETag; perform no encryption or backend I/O |
| Identical concurrent retry while reserved | `OperationAborted` | 409 | `A conflicting operation is in progress; retry the identical part request.` |
| Changed content for claimed part | `OperationAborted` | 409 | `Encrypted multipart part content is immutable; abort this upload and create a new upload.` |
| Legacy encrypted in-flight state | `OperationAborted` | 409 | `This encrypted multipart upload predates nonce-safety state; abort it and create a new upload.` |
| Upload not `open` | `OperationAborted` | 409 | `Multipart upload lifecycle transition is in progress.` |
| Complete selected part absent, uncommitted, or ETag mismatch | `InvalidPart` | 400 | Reject before manifest write and backend Complete |
| Complete parts not strictly ascending | `InvalidPartOrder` | 400 | Reject before state transition |
| State store unavailable | `ServiceUnavailable` | 503 | Existing fail-closed behavior |

All errors use the existing S3 XML body shape and request resource. A mismatch
must not log the claim or plaintext. The structured log may include bucket,
key, upload-ID hash, part number, state version, phase, and revision. This
surface follows S3's documented `OperationAborted`, `InvalidPart`, and
`InvalidPartOrder` semantics [3].

### 3.6 Coordinated rollout

1. Drain or explicitly abort encrypted MPUs before deployment; inventory
   `mpu:*` keys and alert if any version-1/absent-version state remains.
2. Deploy the new binary to all replicas as one coordinated rollout; do not run
   mixed versions because old replicas can still call unconditional
   `AppendPart` and do not understand lifecycle fields.
3. A startup/readiness check reports legacy in-flight count and keeps MPU write
   readiness false while mixed-version deployment is detected via a Valkey
   capability key `mpu:writer-version=2` set with a deployment-scoped value.
4. After all replicas are version 2, enable write readiness. Any surviving
   legacy upload is abort-only and returns HTTP 409 for part writes/Complete.
5. Rollback requires draining/aborting all version-2 in-flight encrypted MPUs
   first; a version-1 binary must never write version-2 state.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Mixed old/new replicas let an old binary bypass reservations with `AppendPart` | Coordinated drain, shared writer-capability gate, all-replica rollout, readiness refusal, and explicit rollback drain; promote to DoD |
| Changed content is encrypted before rejection | Buffer plaintext, compute keyed claim, and complete atomic reservation before constructing the encryptor or calling destination backend; spy-test the ordering; promote to DoD |
| Crash leaves a permanent `reserved` part | Keep upload TTL, conditional token release on ordinary errors, expose in-progress result, and require abort/new upload for owner-unknown stale reservations rather than unsafe takeover |
| A retry returns success although backend part disappeared | Only short-circuit committed retries because backend acknowledged the original write; Complete's backend ETag validation remains authoritative and returns `InvalidPart` if backend state is inconsistent |
| Complete manifest includes overwritten or unselected records | `BeginComplete` atomically validates exact normalized ETags and returns only selected committed records; manifest and backend Complete consume the same snapshot; promote to DoD |
| Lua reads unauthenticated control fields | Mirror version/phase/revision in encrypted metadata and reject disagreement on `Get`; Lua controls atomicity while authenticated metadata detects tampering |
| Lifecycle request crashes after backend Complete | Keep the terminal transition idempotent and conditional; document operator reconciliation. Never reopen after a confirmed backend success |
| UploadPartCopy cannot reject before source backend reads | Document that source reads are required to derive the plaintext claim; guarantee rejection before destination encryption or destination mutation and test those boundaries |
| HMAC claim leaks equality across uploads | Key HMAC with the per-upload DEK and domain-bind part/length; never log/export claims; completed manifest omits them |
| Legacy in-flight uploads become uncompletable | Pre-deploy inventory/drain, abort-only compatibility, actionable 409 message, runbook, and legacy gauge; promote to DoD |
| New state fields accidentally alter completed objects | Keep `MultipartManifest` and encryption framing untouched; golden-test completed bytes/metadata before and after the change; promote to DoD |

## 10. Follow-ups / Out-of-scope items surfaced during planning

1. **Reservation lease/recovery protocol** — a future completed-format version
   could assign a fresh nonce generation and safely recover owner-unknown stale
   reservations; this plan deliberately requires abort/new upload.
2. **Valkey Functions** — migrate embedded Lua to Valkey 7 function libraries
   only if the minimum supported Valkey version changes; `EVALSHA` retains
   current compatibility.
3. **Client-visible strong checksums** — expose S3 checksum algorithms for
   end-to-end client verification independently of the internal keyed claim.
