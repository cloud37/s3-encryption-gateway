## 1. Context & Current State

The current single-PUT chunked format is a concatenation of independently
authenticated data chunks. `ChunkManifest.Version` is written as `1`
(`internal/crypto/chunked.go:35-43,97-103`), each chunk nonce is derived from
the base IV and chunk index (`internal/crypto/chunked.go:116-134`), and
encryption calls `AEAD.Seal` with no AAD (`internal/crypto/chunked.go:331-342`).
Decryption likewise reads until backend EOF and calls `AEAD.Open` with no AAD
(`internal/crypto/chunked.go:520-607,611-618`). Every present chunk is
authenticated, but EOF itself is not. Removing one or more complete trailing
chunks therefore yields a shorter stream whose remaining tags all verify; the
reader reports ordinary EOF rather than proving that the object is complete.
That is insufficient for authenticated object semantics: GCM authenticates
the ciphertext and AAD supplied to a particular invocation, not the expected
number of independently sealed records [1][3].

The write path snapshots the manifest before the streaming reader has consumed
any plaintext, so the persisted manifest and metadata do not contain the final
chunk count (`internal/crypto/engine.go:1065-1103`). Read paths compensate with
inferred counts and sizes. `decryptChunked` derives plaintext size directly
from ciphertext length (`internal/crypto/engine.go:1433-1466`),
`GetPlaintextSizeFromMetadata` returns either metadata or a chunk-count upper
bound (`internal/crypto/range_optimization.go:171-199`), and the HTTP layer has
another ciphertext-to-plaintext implementation
(`internal/api/handlers.go:2816-2847`). HEAD repeats the formula inline
(`internal/api/handlers.go:2334-2371`). These formulas assume only a 16-byte
tag per data chunk; appending a terminal record requires one format-aware,
overflow-checked implementation used by crypto, GET, range, HEAD, copy, and
UploadPartCopy.

Range decryption authenticates only selected data chunks. The optimized range
calculation maps plaintext chunks directly to ciphertext offsets
(`internal/crypto/range_optimization.go:32-110`), and `rangeDecryptReader`
returns after the requested end chunk (`internal/crypto/range_decrypt.go:126-218`).
ADR 0001 explicitly chose verification of only the chunks touched by a range
(`docs/adr/0001-range-optimization-design.md:54-57`); that decision cannot
detect suffix truncation. Current GET sends success headers before a full
stream has reached EOF (`internal/api/handlers.go:1570-1605`), HEAD returns
metadata without reading object bytes (`internal/api/handlers.go:2263-2441`),
CopyObject begins decrypt-and-reencrypt after a source GET
(`internal/api/handlers.go:5132-5287`), and both chunked UploadPartCopy branches
decrypt a selected plaintext range without authenticating an object-level end
record (`internal/api/upload_part_copy.go:496-576,736-827`).

The objective is a version-2 chunked format with an authenticated, fixed-size
terminal record that commits to the exact data-chunk count and plaintext size.
New data records also bind their format version, record domain, and index as
AAD, while nonce derivation is domain separated through HKDF `info` as advised
by RFC 5869 [2]. Version 1 remains readable because persisted objects are an
external compatibility contract, but its inability to prove suffix
completeness is documented and classified for GET-through-gateway followed by
PUT-through-gateway re-encryption. Any format version other than 1 or 2 fails
closed. ADR 0016 will supersede the affected format and authentication portions
of ADR 0001 without changing its range-performance objective.

## 2. Design Goals & Non-Goals

### Goals

1. **Authenticated completeness for new objects** — every v2 object ends in a
   32-byte AES-256-GCM record authenticating the exact `uint64` data-chunk
   count and exact `uint64` plaintext size.
2. **Domain separation** — v2 data chunks and the terminal use distinct HKDF
   nonce labels and distinct, versioned AAD; a terminal cannot be accepted as
   a data chunk or moved between format versions [2][3].
3. **Fail-closed versioning** — manifests with versions other than 1 or 2 are
   rejected before plaintext, headers, destination writes, or copy success is
   produced.
4. **Read-path enforcement** — v2 full GET, ranged GET, HEAD, CopyObject, and
   both chunked UploadPartCopy strategies authenticate the terminal before
   success; full streaming decryption independently verifies the terminal at
   EOF and compares it with observed data.
5. **One size model** — crypto and API code use shared, overflow-checked v1/v2
   functions for plaintext size, ciphertext size, data-record count, and
   encrypted data ranges.
6. **Explicit compatibility** — v1 remains readable with unchanged legacy
   nonce/AAD behavior, is identified as migration-required, and has its
   suffix-truncation limitation documented.
7. **Bounded operation** — encryption and full decryption remain streaming;
   preflight reads exactly the 32-byte v2 trailer and ranges continue to fetch
   only the requested data chunks plus that separate trailer request.
8. **Deterministic interoperability** — byte order, labels, AAD layouts, empty
   object behavior, size equations, and error behavior are fixed by ADR 0016
   and known-answer tests.

### Non-Goals

1. **Retrofitting a terminal onto v1 ciphertext in place** — v1 data records
   use a different authentication domain; safe upgrade requires plaintext GET
   followed by PUT and is documented rather than mutating stored suffix bytes.
2. **Changing multipart-encryption format** — `MetaMPUEncrypted` objects use a
   separate part manifest and nonce schedule; this issue covers only
   `MetaChunkedFormat` single-PUT objects.
3. **Authenticating arbitrary user metadata in the terminal** — existing
   metadata protection remains unchanged; the terminal commits only to stream
   completeness fields required by this issue.
4. **Eliminating copy buffering limits** — existing backend signing and
   `maxCopyPartRangeBytes` constraints remain; this work adds authentication
   before those bounded reads.
5. **Removing v1 reads** — removal needs a separately announced compatibility
   window after operators can classify and re-encrypt legacy objects.

## 3. Target Interface / Semantics / Behaviour

### 3.1 Version and error contract

Add the following public crypto contract in `internal/crypto/chunked.go`:

```go
const (
	ChunkedFormatV1       uint8 = 1
	ChunkedFormatV2       uint8 = 2
	ChunkedTerminalSize         = 32
	chunkedTerminalPlainSize    = 16
)

var (
	ErrUnsupportedChunkedVersion = errors.New("unsupported chunked format version")
	ErrChunkedObjectIncomplete    = errors.New("chunked object completeness check failed")
)

type ChunkedObjectInfo struct {
	Version       uint8
	ChunkCount    uint64
	PlaintextSize uint64
	Authenticated bool
}

func ChunkedFormatVersion(metadata map[string]string) (uint8, error)
```

`ChunkedFormatVersion` expands only the existing manifest representation: a
decoded manifest version of `1` means v1, `2` means v2, and all other values,
including zero, return `ErrUnsupportedChunkedVersion`. Missing or malformed
manifests retain their existing descriptive errors. `Authenticated` is false
only for accepted v1 objects and true only after a v2 terminal tag verifies.
The explicit result prevents callers from accidentally presenting inferred v1
size as authenticated completeness.

Rationale: the manifest already owns format versioning
(`internal/crypto/chunked.go:35-43`), so adding a second metadata version would
create contradictory authorities. Sentinel errors permit HTTP translation and
`errors.Is` tests without matching crypto-library text.

### 3.2 Version-2 wire format

For chunk size `S`, data chunk index `i`, data plaintext `P_i`, 32-byte object
DEK `K`, and 12-byte manifest base IV `B`, the stored bytes are:

```text
DataRecord_0 || ... || DataRecord_(N-1) || TerminalRecord

DataRecord_i  = AES-GCM-or-selected-AEAD(K).Seal(
                  nonce=DataNonce(B, i), plaintext=P_i, aad=DataAAD(i))
TerminalPlain = uint64_be(N) || uint64_be(sum(len(P_i)))
TerminalRecord= AES-256-GCM(K).Seal(
                  nonce=TerminalNonce(B), plaintext=TerminalPlain,
                  aad=TerminalAAD())
```

The terminal plaintext is exactly 16 bytes and AES-GCM appends a 16-byte tag,
therefore `TerminalRecord` is always exactly 32 bytes. The terminal primitive
is AES-256-GCM even when the selected data-chunk algorithm is different; the
existing object DEK is 32 bytes in either supported data algorithm
(`internal/crypto/engine.go:974-978`). Empty plaintext has `N=0`, size `0`, no
data records, and one valid terminal record.

The exact nonce and AAD builders are:

```go
func deriveChunkNonceHKDF(baseIV []byte, version uint8, chunkIndex uint64) ([]byte, error)
func deriveTerminalNonceHKDF(baseIV []byte, version uint8) ([]byte, error)
func buildChunkAAD(version uint8, chunkIndex uint64) []byte
func buildTerminalAAD(version uint8) []byte
func encodeChunkedTerminal(chunkCount, plaintextSize uint64) [chunkedTerminalPlainSize]byte
func decodeChunkedTerminal(plaintext []byte) (chunkCount, plaintextSize uint64, err error)
```

All integer fields use network byte order. For v2, the HKDF-SHA-256 `info`
values are, byte for byte:

```text
DataNonce info     = "chunked-v2/data-nonce" || 0x00 || uint64_be(i)
TerminalNonce info = "chunked-v2/terminal-nonce" || 0x00
DataAAD            = "chunked-v2/data" || 0x00 || uint64_be(i)
TerminalAAD        = "chunked-v2/terminal" || 0x00
```

The HKDF output length is the AEAD nonce size and must be 12 for the required
AES-GCM terminal. Version 1 continues to use its current
`"chunk-iv" || uint32_be(i)` HKDF input and nil AAD solely for reads. Version 2
rejects a chunk index that cannot be represented as `uint64`; implementation
counters are changed from `int` to `uint64` so no narrowing conversion occurs.
RFC 5869 states that `info` binds derived material to application context [2],
while RFC 5116 requires unambiguous AAD construction and unique nonces [3].

Rationale: fixed labels plus fixed-width fields make each AAD injective and
each nonce domain disjoint. Committing count and total size in one final AEAD
record detects complete-chunk suffix deletion, terminal deletion, terminal
substitution, and data/terminal record confusion while preserving streaming.

### 3.3 Streaming reader behavior

Change constructors to carry the explicit format version:

```go
func newChunkedEncryptReaderWithContext(
	ctx context.Context, source io.Reader, aead cipher.AEAD,
	baseIV []byte, chunkSize int, formatVersion uint8,
	bufferPool *BufferPool,
) (*chunkedEncryptReader, *ChunkManifest, error)

func newChunkedDecryptReaderWithContext(
	ctx context.Context, source io.Reader, dataAEAD cipher.AEAD,
	terminalAEAD cipher.AEAD, manifest *ChunkManifest,
	bufferPool *BufferPool,
) (*chunkedDecryptReader, error)
```

The encrypt reader emits v2 data records, counts plaintext bytes and records
with checked `uint64` addition, then emits exactly one terminal record before
EOF. It writes manifest version 2 before metadata is snapshotted. Source read,
counter overflow, HKDF, or terminal seal errors terminate the stream without a
successful EOF.

The full decrypt reader parses by manifest version. V1 retains current behavior.
V2 keeps a 32-byte look-behind so the final bytes are never scheduled as a data
record, authenticates every data record using v2 nonce/AAD, authenticates the
terminal, and compares terminal count/size against observed count/size before
returning EOF. Missing, short, extra, malformed, or mismatching terminal data
returns an error wrapping `ErrChunkedObjectIncomplete`. No terminal plaintext
is returned to the caller.

Rationale: preflight protects status-returning operations before success, but
the stream itself must remain self-verifying for non-HTTP callers and for any
backend mutation between preflight and the full GET. This is a deliberate
time-of-check/time-of-use defense, not duplicate optional validation.

### 3.4 Trailer authentication interface

Extend `EncryptionEngine` and its passthrough implementation:

```go
type EncryptionEngine interface {
	// Existing methods remain unchanged.
	AuthenticateChunkedTrailer(
		ctx context.Context,
		trailer io.Reader,
		metadata map[string]string,
		ciphertextSize int64,
	) (ChunkedObjectInfo, error)
}
```

For v2, the method expands/decrypts metadata exactly as `decryptChunked` does,
derives or unwraps the DEK with context propagation, constructs an independent
AES-256-GCM terminal AEAD, reads exactly 32 bytes plus a one-byte over-read,
opens it with the terminal nonce/AAD, validates terminal count/size against the
centralized size model and `ciphertextSize`, zeroizes the DEK, and returns an
authenticated `ChunkedObjectInfo`. A short/long trailer, failed tag, impossible
count, impossible size, or arithmetic overflow wraps
`ErrChunkedObjectIncomplete`. Unknown versions return
`ErrUnsupportedChunkedVersion`. V1 consumes no trailer and returns its inferred
info with `Authenticated=false`; `PassthroughEngine` returns a descriptive
not-chunked error because API code invokes this method only after chunked
classification.

Rationale: placing key resolution and AEAD verification inside crypto avoids
exposing DEKs to handlers or duplicating password/KMS behavior. Extending the
small interface forces every implementation and test double to define the
security behavior rather than relying on an optional type assertion.

### 3.5 Central size and range arithmetic

Add these checked helpers to `internal/crypto/range_optimization.go`:

```go
func ChunkedDataChunkCount(plaintextSize int64, chunkSize int) (uint64, error)
func ChunkedCiphertextSize(plaintextSize int64, chunkSize int, version uint8) (int64, error)
func ChunkedPlaintextSize(ciphertextSize int64, chunkSize int, version uint8) (int64, uint64, error)
func ChunkedEncryptedDataRange(startChunk, endChunk uint64, chunkSize int, version uint8) (int64, int64, error)
```

The equations are:

```text
N      = 0                              when plaintextSize == 0
N      = ceil(plaintextSize / S)        otherwise
v1 CT  = plaintextSize + N*16
v2 CT  = plaintextSize + N*16 + 32
```

Inverse v2 arithmetic first subtracts 32 and then solves the same v1 data
equation. Every helper rejects negative sizes, invalid chunk sizes, unsupported
versions, non-canonical ciphertext lengths, and overflow before multiplication
or addition. For v2, encrypted data ranges never include the terminal; callers
fetch it separately. `GetPlaintextSizeFromMetadata` prefers an exact centralized
calculation when backend `Content-Length` and version are present, then retains
`MetaOriginalSize` as the v1 compatibility fallback. The API-local
`chunkedPlaintextSizeFromCiphertext`, `plaintextSizeFromCiphertextMetadata`,
and duplicated HEAD formula are removed.

Rationale: wire-format overhead is cryptographic protocol state. A single
version-aware implementation prevents HEAD, GET, and range routing from
disagreeing about whether the 32-byte terminal is plaintext or data ciphertext.

### 3.6 HTTP and copy preflight contract

Add one handler helper:

```go
func (h *Handler) preflightChunkedCompleteness(
	ctx context.Context,
	s3Client s3.Client,
	bucket, key string,
	versionID *string,
	metadata map[string]string,
) (crypto.ChunkedObjectInfo, error)
```

For v2, it parses backend `Content-Length`, requests exactly
`bytes=(ciphertextSize-32)-(ciphertextSize-1)` through `GetObject`, passes that
reader to `AuthenticateChunkedTrailer`, closes the reader on every path, and
returns only authenticated info. V1 performs no suffix request, returns
`Authenticated=false`, and remains readable under the documented limitation.
Unknown versions and all v2 verification failures fail closed.

| Operation | Required placement and behavior |
|---|---|
| Full GET | After encrypted metadata and backend length are known but before `WriteHeader(200)`, preflight v2; then stream full decrypt, which verifies again at EOF. |
| Ranged GET | During existing HEAD-based range planning, preflight v2 before fetching/writing selected data chunks; use authenticated trailer size/count for range validation and `Content-Range`. |
| HEAD | After backend HeadObject and before setting response headers, preflight v2 and use authenticated plaintext size; return no success headers on failure. |
| CopyObject | Head and preflight the encrypted chunked source before source decryption, destination encryption, or `PutObject`; full streaming decrypt still verifies the terminal. |
| UploadPartCopy | In `classifyCopySource`, preflight v2 before selecting either `uploadPartCopyChunked` or the chunked arm of `uploadPartCopyReencryptMPU`; no destination part or state record is written first. |

For a v2 completeness or unknown-version failure, all five operations return
the existing S3 XML `InternalError`, HTTP 500, and message `Object integrity
check failed`; HEAD has an empty body as required by HTTP semantics. They record
the existing encryption-error metric with reason
`chunked_completeness_failed`. Authentication/authorization and source-not-found
errors retain existing translation. V1 operations succeed when their accessed
data tags verify; documentation must state that complete trailing-chunk removal
cannot be detected for v1.

Rationale: range and HEAD cannot discover a missing suffix by reading selected
data records, and CopyObject can otherwise turn a truncated source into a
valid new destination. A fixed 32-byte preflight is bounded and lets all
status-returning paths reject corruption before observable success.

### 3.7 Migration classification

Extend the read-only object classifier:

```go
const (
	// Existing constants remain in their current order and values.
	ClassE_ChunkedV1 ObjectClass = ClassUnknown + 1
)
```

`ClassifyObject` calls `crypto.ChunkedFormatVersion` for otherwise-modern
chunked metadata. V1 becomes `ClassE_ChunkedV1`, v2 remains `ClassModern`, and
an unsupported or malformed manifest becomes `ClassUnknown`. Existing higher
priority classes (fallback, no-AAD, XOR nonce derivation, and legacy KDF)
remain higher priority so one object is not silently removed from an already
required migration class. `ClassToString(ClassE_ChunkedV1)` returns
`"class_e_chunked_v1"`, and `NeedsMigration` returns true.

Rationale: classification is advisory and must not alter read behavior. Giving
v1 a stable class lets operators identify objects that need ordinary
GET-through-gateway followed by PUT-through-gateway re-encryption without
reintroducing a second encryption implementation.

### Tier 2 conformance

Tier 2 tests use the `conformance` build tag through the repository Make
targets and live in exactly one tier. Test bodies have signature
`func testXxx(t *testing.T, inst provider.Instance)`, are registered in the
`cases` slice in `test/conformance/suite_test.go`, never branch on provider
name, and use capability bits rather than provider-specific exceptions.
Docker unavailability calls `t.Skip` naming the missing fixture. Direct
backend mutation uses common S3 operations and `provider.Instance` connection
details, never `Instance.Raw`, vendor administration APIs, hard-coded ports,
backend binaries, or docker-compose. The complete Tier 2 run must remain below
15 minutes.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| A v2 writer is deployed before all readers understand v2, making new objects unreadable on old instances. | Treat B1/B2 and ADR 0016 as one atomic release unit; require mixed-version rollout guidance to drain old readers before enabling writers, and add a changelog compatibility warning. |
| Parallel data encryption emits records out of index order or terminal before all workers complete. | Preserve ordered job consumption, wait for all pending jobs, derive AAD from the job's absolute `uint64` index, and emit the terminal only after the pending channel is exhausted; known-answer and concurrent tests verify order. |
| The terminal nonce collides with a data nonce under the same DEK/base IV. | Use disjoint fixed HKDF `info` domains and known-answer tests proving different outputs for index values including 0 and `math.MaxUint64` [2]. |
| Trailer preflight authenticates one object version while the data request reads another. | Pass the exact `versionID` to HEAD, trailer GET, and data GET; test version preservation. Full streaming verification detects same-key mutation after preflight. |
| HEAD and range responses expose authenticated-looking sizes for v1. | Carry `Authenticated` explicitly, document v1 values as inferred, classify v1 for migration, and never log or label v1 as completeness-verified. |
| Duplicated old arithmetic subtracts only per-chunk tags and accidentally counts the v2 terminal as plaintext. | Delete API-local formulas, use only §3.5 helpers, and make v1/v2 boundary and inverse tests mandatory. |
| Optimized ranges accidentally include or decrypt the terminal as a data record. | Keep data-range calculation terminal-exclusive, fetch the terminal separately, and test a one-byte range at the final plaintext byte. |
| A malformed count/size causes integer overflow or excessive allocation. | Parse as fixed `uint64`, validate against checked ciphertext equations before conversion, reject values above `math.MaxInt64`/platform `int`, and never allocate from terminal fields. |
| CopyObject or UploadPartCopy writes destination data before discovering source truncation. | Preflight before destination encryption, `PutObject`, `UploadPart`, or `AppendPart`; mocks assert zero destination calls on failure. |
| Full GET sends 200 before a later stream verification error. | Preflight before headers and verify again while streaming. If the backend changes after preflight, terminate the connection and record the existing encryption error; HTTP status cannot be changed after streaming begins. |
| Metadata compaction or encrypted metadata hides the manifest from handler code. | Handlers pass raw metadata to the engine; format parsing and metadata expansion remain inside crypto. The API helper uses only backend `Content-Length` before engine verification. |
| Extending `EncryptionEngine` breaks test doubles or alternate engines. | Update the concrete passthrough engine and every repository test double found at `internal/api/sec20_test.go:19-32` and `internal/api/upload_part_copy_test.go:703-712`; compile all packages and tags. |
| V1 classification masks an older, higher-priority migration requirement. | Preserve current fallback/no-AAD/XOR/KDF precedence and add explicit precedence tests before returning Class E. |
| Operators append 32 bytes to v1 and assume it is upgraded. | ADR and migration guide state that v2 changes data AAD/nonces and requires GET→PUT re-encryption; classifier checks manifest version, not object length. |

## 8. Definition of Done

- [ ] Per `docs/issues/v1.0-issues.md`, all newly written single-PUT
      chunked objects use manifest v2 and end in exactly one 32-byte
      AES-256-GCM terminal record.
- [ ] The terminal authenticates exact big-endian `uint64` chunk count and
      plaintext size, including `(0,0)` for an empty object.
- [ ] V2 data and terminal nonce derivations use the exact disjoint HKDF labels
      in §3.2, and v2 data/terminal AAD uses the exact versioned domains.
- [ ] V2 full decryption verifies every data tag and the terminal before clean
      EOF and rejects missing, short, extra, substituted, or inconsistent
      records with `ErrChunkedObjectIncomplete`.
- [ ] Full GET, ranged GET, HEAD, CopyObject, regular chunked UploadPartCopy,
      and encrypted-MPU-destination UploadPartCopy preflight v2 terminal
      authentication before returning success or writing destination data.
- [ ] Full GET performs streaming terminal verification after preflight and
      terminates a changed/corrupt stream rather than reporting clean EOF.
- [ ] Source `versionID` is identical across metadata, trailer, and data reads.
- [ ] Unknown manifest versions fail closed in full decrypt, range decrypt,
      GET, HEAD, CopyObject, and UploadPartCopy; no plaintext or destination
      write occurs first.
- [ ] V1 fixtures remain readable with their existing HKDF nonce derivation and
      nil AAD, and docs explicitly state that v1 cannot authenticate complete
      trailing-chunk presence.
- [ ] V1 objects classify as `class_e_chunked_v1` and migration-required unless
      an existing higher-priority legacy class applies; v2 is modern and
      malformed/unsupported versions are unknown.
- [ ] All chunked plaintext/ciphertext/count/range arithmetic is centralized in
      `internal/crypto/range_optimization.go`; duplicate API and HEAD formulas
      are removed.
- [ ] Arithmetic rejects overflow, negative/non-canonical lengths, invalid
      chunk sizes, and unsupported versions without allocation from attacker-
      controlled terminal fields.
- [ ] Copy paths make zero `PutObject`, `UploadPart`, and `AppendPart` calls
      after a failed source completeness check.
- [ ] DEKs used for preflight and streaming are zeroized on every success and
      error path, and context cancellation propagates through key unwrapping.
- [ ] ADR `docs/adr/0016-authenticated-chunked-completeness.md` is accepted and
      contains the byte-exact protocol, compatibility decision, deployment
      sequencing, and superseded portions of ADR 0001.
- [ ] `docs/ENCRYPTION_DESIGN.md`, `docs/MIGRATION.md`, and `CHANGELOG.md` are
      updated with v2 semantics, v1 limitation/classification, and GET→PUT
      upgrade instructions.
- [ ] Every exact test named in §6 passes under `-race`; SEC-37 branch coverage
      in touched `internal/crypto` and `internal/api` code is at least 85%.
- [ ] All Tier 2 functions in §6 are registered in
      `test/conformance/suite_test.go`, use the documented capabilities, and
      pass `make test-conformance-local` without provider-name branches.
- [ ] `make test-isolation-check` passes; conformance tests use Testcontainers
      fixtures and portable S3 operations only.
- [ ] Default, `fips`, and `hsm` compile/test commands, `go vet` (default and
      FIPS), and `golangci-lint run` complete cleanly.

## 10. Follow-ups / Out-of-scope items surfaced during planning

1. **Retire v1 reads after measured migration completion** — define a future
   release gate using classifier results and a documented deprecation window;
   this plan intentionally keeps v1 readable.
2. **Authenticate multipart-object global completeness** — the separate MPU
   ciphertext/manifest format should be reviewed for an equivalent final
   commitment, but changing it here would couple two wire-format migrations.
3. **Close HTTP mid-stream integrity observability uniformly** — standardize
   audit/metric handling for any post-header AEAD failure across single-PUT and
   MPU streams; this plan uses the existing encryption-error surface.
4. **Avoid duplicate backend reads for full GET** — a future backend capability
   could combine trailer preflight and a stable-version full stream, but it
   must preserve the before-success guarantee and version identity.
