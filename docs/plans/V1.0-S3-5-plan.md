## 1. Context & Current State

The router already maps generic `PUT /{bucket}` to `handleCreateBucket` and
`DELETE /{bucket}` to `handleDeleteBucket`, after query-specific bucket routes
(`internal/api/handlers.go:282`, `internal/api/handlers.go:354`). Route ordering
must remain intact so `PUT /bucket?versioning` is not misclassified as creation.

CreateBucket is intentionally synthetic. In `PROXIED_BUCKET` mode it returns
409 for the configured bucket and 501 for every other bucket. Otherwise it
calls `ListObjects(MaxKeys:1)` as an existence probe, maps every probe error to
501, and returns 409 on success (`internal/api/handlers.go:2821`). It never
forwards CreateBucket, cannot preserve LocationConstraint, and conflates
NoSuchBucket, AccessDenied, and transport failure.

DeleteBucket already forwards through the raw passthrough path after an optional
policy warning (`internal/api/handlers.go:5406`). It has no explicit management
authorization. The backend `s3.Client` interface has no CreateBucket or
DeleteBucket methods (`internal/s3/client.go:35`); passthrough preserves path,
query, body, headers, re-signs with backend credentials, and returns raw backend
semantics (`internal/api/utils.go:137`). For the tiny CreateBucket XML body this
is the narrowest implementation and naturally preserves LocationConstraint.

The feature must not become an account-wide bucket-creation endpoint. Effective
creation permission requires a default-false global gate, matching V1.0-AUTH-2
scope, and explicit `bucket_permissions:create`. Deletion independently requires
scope and `bucket_permissions:delete`; object `rw` grants neither. Every denial
must occur before backend access, following least privilege [1][2].

## 2. Design Goals & Non-Goals

### Goals

1. Preserve the current safe default: bucket creation remains disabled.
2. Forward authorized CreateBucket without a racy existence probe.
3. Require global enablement, target scope, and explicit `create` capability.
4. Require target scope and explicit `delete` capability for DeleteBucket.
5. Validate generic S3-safe bucket names before forwarding.
6. Preserve request body, query, relevant headers, and backend response/error semantics.
7. Ensure every unauthorized or disabled request makes zero backend calls.
8. Cover provider differences with capability-gated conformance tests.

### Non-Goals

1. Shipping before V1.0-AUTH-2; the prerequisite is a hard security boundary.
2. Inferring management permissions from object `rw`.
3. Automatically creating encryption policy entries for new buckets; normal
   name-based policy matching applies as it does for out-of-band buckets.
4. Implementing provider-specific LocationConstraint rewriting; the backend owns it.
5. Adding CreateBucket/DeleteBucket to every `s3.Client` adapter; raw signed
   passthrough preserves provider-specific wire behavior with less surface.
6. A global DeleteBucket toggle; deletion is governed by explicit credential permission.

## 3. Target Interface / Semantics / Behaviour

### Configuration contract

```yaml
allow_bucket_creation: false

auth:
  credentials:
    - access_key: service-a
      secret_key_env: SERVICE_A_SECRET
      buckets: [app-service-a, app-*]
      permissions: rw
      bucket_permissions: [create, delete]
```

```text
CreateBucket allowed = ALLOW_BUCKET_CREATION
                       AND target matches effective credential scope
                       AND bucket_permissions contains create

DeleteBucket allowed = target matches effective credential scope
                       AND bucket_permissions contains delete
```

`allow_bucket_creation` maps to `ALLOW_BUCKET_CREATION`, defaults to false in
all config/Helm paths, and may be enabled independently of whether any credential
has `create`. `PROXIED_BUCKET` remains an additional intersection, so at most
that bucket can be created in single-bucket mode.

Rationale: the global gate lets operators opt into the expanded backend
capability, while the credential grant constrains who can use it and for which
names. The two controls are intentionally independent.

### Request/response contract

| Request/state | Result | Backend contacted? |
|---|---|---|
| CreateBucket global gate false | HTTP 501 `NotImplemented` (compatibility default) | no |
| Gate true, scope mismatch | HTTP 403 `AccessDenied` | no |
| Gate true, no explicit create | HTTP 403 `AccessDenied` | no |
| Gate true, authorized, invalid name | HTTP 400 `InvalidBucketName` | no |
| Gate true, authorized, valid | Forward original request and backend result | yes |
| DeleteBucket scope mismatch/no delete | HTTP 403 `AccessDenied` | no |
| DeleteBucket authorized | Forward original request and backend result | yes |

Disabled creation retains 501 to avoid changing the established default. Once
enabled and authorized, the gateway must not probe existence. The backend decides
`BucketAlreadyExists`, `BucketAlreadyOwnedByYou`, region constraints, status,
headers, and XML. A nonempty `CreateBucketConfiguration` body is forwarded
byte-for-byte; an empty body remains empty. Client auth artifacts are stripped
and the request is re-signed using backend credentials, as in existing
`forwardToBackend` (`internal/api/utils.go:176`).

### Bucket validation

```go
func ValidateBucketName(name string) error
```

The validator enforces the generic S3-safe subset before backend access:
length 3-63; lowercase ASCII letters, digits, dot, and hyphen only; begins and
ends alphanumeric; no adjacent dots; no dot-hyphen/hyphen-dot sequence; not an
IPv4 address. Reserved provider/AWS prefixes and suffixes should be included
only if the project explicitly claims current AWS naming parity; otherwise the
backend remains authoritative for provider-specific restrictions.

Rationale: local syntax validation prevents malformed or typo-like names from
reaching a privileged account, while backend validation retains compatibility
across S3 providers [3].

### Passthrough helper contract

Use the existing signed raw passthrough rather than extending `s3.Client`.
Create a helper that accepts the already-authorized operation and records
semantic metrics/audit once. Do not allow handlers to call it until V1.0-AUTH-2
authorization has succeeded. The request body is small but remains bounded by a
new constant (for example 64 KiB) to avoid turning generic buffering into an
unbounded body sink.

## 4. Work Breakdown

### Phase A — Prerequisite verification and safe-default config

- **A1 — verify V1.0-AUTH-2 DoD:** do not begin handler changes until principal
  context, scope matching, explicit grants, and zero-backend-on-denial tests pass.
- **A2 — edit `internal/config/config.go`:** add
  `AllowBucketCreation bool` with YAML/env contract and explicit false default.
- **A3 — edit `internal/config/config_test.go`:** test default, YAML, env, and
  reload behavior; enabling the gate is a reload-safe non-crypto change.
- **A4 — edit `cmd/server/main.go`:** ensure the live handler reads the reloaded
  gate or apply it through atomic runtime config; document restart if runtime
  handler config cannot safely update.

### Phase B — Bucket validation and authorized handlers

- **B1 — new `internal/api/bucket_name.go`:** implement generic bucket-name validation.
- **B2 — new `internal/api/bucket_name_test.go`:** table-test valid and invalid names.
- **B3 — edit `internal/api/handlers.go`:** replace enabled CreateBucket probe
  with authorized passthrough; retain 501 with no backend call when disabled.
- **B4 — edit `internal/api/handlers.go`:** require explicit delete before the
  policy warning and passthrough; do not disclose policy IDs on denied requests.
- **B5 — edit `internal/api/utils.go`:** add a bounded request-body option for
  CreateBucket passthrough and preserve raw LocationConstraint bytes.
- **B6 — edit `internal/api/handlers_test.go` and `internal/api/utils_test.go`:**
  assert the full authorization/error/body/headers matrix with atomic backend call counts.

Phase B depends on A1 and V1.0-AUTH-2's context helpers.

### Phase C — Metrics, audit, and conformance

- **C1 — edit `internal/api/handlers.go`:** emit semantic CreateBucket and
  DeleteBucket success/error metrics; integrate V1.0-OBS-2 route metrics when available.
- **C2 — edit audit tests:** verify allowed and denied management attempts record
  operation, bucket, credential label, result, and no secrets.
- **C3 — edit `test/provider/provider.go`:** add `CapBucketManagement` so
  positive provider tests run only where credentials permit create/delete.
- **C4 — edit `test/harness/options.go` and `test/harness/gateway.go`:** add
  typed options for creation gate and credential authorization policy.
- **C5 — edit `test/conformance/s3_compat_test.go` and suite registration:**
  replace the misleading direct-backend DeleteBucket test with gateway-facing
  create/delete authorization scenarios.

### Phase D — Helm and documentation

- **D1 — edit Helm values/schema/deployment:** expose
  `config.allowBucketCreation`, default false, and render `ALLOW_BUCKET_CREATION`.
- **D2 — edit Helm tests:** verify false default, enabled rendering, explicit
  create/delete fields, and no inference from `rw`.
- **D3 — edit `config.yaml.example`, `README.md`, `docs/DEPLOYMENT.md`,
  `docs/ARCHITECTURE.md`, `docs/S3_API_IMPLEMENTATION.md`, and chart README:**
  document the three-part creation gate, independent deletion, backend IAM, and
  LocationConstraint passthrough.
- **D4 — edit `CHANGELOG.md`:** add V1.0-S3-5 under Unreleased.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Global flag enables arbitrary creation | Require all three gates and verify zero backend calls on denial. |
| `rw` accidentally grants account management | Keep typed bucket permissions independent and test non-inference. |
| Existing DeleteBucket remains unrestricted | Gate it with explicit delete before policy logging/passthrough. |
| Existence probe races or masks AccessDenied | Remove probe entirely from enabled path; backend owns result. |
| LocationConstraint is altered | Forward body byte-for-byte and test empty/nonempty cases. |
| Malformed names reach privileged backend | Validate generic S3-safe syntax before passthrough. |
| Raw body buffering is abused | Enforce a small CreateBucket body limit before allocation. |
| Provider credentials cannot manage buckets | Gate positive conformance tests with `CapBucketManagement`. |
| Global single-bucket mode is bypassed | Require effective scope intersection from V1.0-AUTH-2. |

## 10. Follow-ups / Out-of-scope items surfaced during planning

- Consider an independent global DeleteBucket safety gate if operators request
  defense in depth beyond explicit per-credential deletion grants.
- Raw passthrough does not use GCS/Azure shim methods; provider-specific bucket
  management adapters require separate design if those backends need support.
- Bucket ownership controls, object-lock creation options, and account-level
  quotas remain backend responsibilities.
