# V1.0-OBS-2 — Per-Bucket Request and Client Traffic Metrics — Implementation Plan

Status: Draft
Owner: Observability / API
Priority: P1
Labels: `milestone:v1.0`, `area:observability`, `area:api`, `area:helm`

> Scope clarified relative to `docs/issues/v1.0-issues.md:55` and GitHub
> issue #230. The gateway already has semantic operation/bucket metrics; this
> plan fills request-status and client-visible byte gaps without changing any
> existing Prometheus label schema.

---

## 1. Context & Current State

The requested semantic operation dimension largely exists. The gateway exposes
`s3_operations_total{operation,bucket}`,
`s3_operation_duration_seconds{operation,bucket}`, and
`s3_operation_errors_total{operation,bucket,error_type}`
(`internal/metrics/metrics.go:218`). `RecordS3Operation` and `RecordS3Error`
collapse bucket values to `"*"` when bucket labels are disabled
(`internal/metrics/metrics.go:769`). These metric names and labels are deployed
interfaces and must remain unchanged.

The HTTP metrics do not meet the requested contract. They use method, sanitized
path, and status text (`internal/metrics/metrics.go:196`), and
`http_request_bytes_total` has only method/path labels. `RecordHTTPRequest`
adds a caller-supplied byte count (`internal/metrics/metrics.go:720`), which is
often backend `ContentLength`, zero when unknown, or ciphertext rather than
client-visible plaintext. Passthrough discards the actual `io.Copy` count and
then records `resp.ContentLength` (`internal/api/utils.go:121`,
`internal/api/utils.go:291`).

Semantic coverage is also incomplete. Core object and multipart handlers call
`RecordS3Operation`, but generic passthrough receives an operation name and
records only HTTP/audit metrics (`internal/api/utils.go:256`). Consequently
ListBuckets, DeleteBucket, bucket subresources, object tagging/ACL passthrough,
and several local errors are absent from complete operation/status dashboards.
Existing success/error metric meaning must not be redefined retroactively.

The objective is to add two stable client-facing metric families, count actual
bytes at the HTTP boundary, cover every matched S3 route exactly once, preserve
bounded cardinality, and expose useful per-bucket Grafana panels [1][2].

## 2. Design Goals & Non-Goals

### Goals

1. Record every completed S3 route once by semantic operation, bucket, and
   numeric client-visible status.
2. Record actual plaintext application bytes consumed from and written to clients.
3. Count decoded AWS streaming upload bytes, not SigV4 chunk framing/signatures.
4. Avoid double-counting backend retries, seekable-body rereads, or internal copies.
5. Preserve every existing metric name, label set, and interpretation.
6. Reuse `METRICS_ENABLE_BUCKET_LABEL`; disabled mode emits `bucket="*"`.
7. Keep labels bounded and free of keys, paths, upload IDs, credentials, and text errors.
8. Add per-bucket dashboard filtering and throughput/error panels.

### Non-Goals

1. Removing or redefining `http_request_bytes_total`; it remains a legacy metric.
2. Adding labels to existing metric families; that is a breaking schema change.
3. Measuring TLS, HTTP headers, chunk framing, or network retransmission bytes.
4. Counting backend ciphertext traffic; this plan measures the client boundary.
5. Per-bucket alert rules; dashboards land first and alerts can follow after field data.

## 3. Target Interface / Semantics / Behaviour

### New metric families

```text
s3_client_requests_total{operation,bucket,status_code}
s3_client_bytes_total{bucket,direction}
```

| Metric | Meaning |
|---|---|
| `s3_client_requests_total` | One increment for each completed matched S3 route; `status_code` is a numeric string such as `200` or `404`. |
| `s3_client_bytes_total direction=in` | S3 application-body bytes actually consumed from the client after AWS streaming framing is decoded. |
| `s3_client_bytes_total direction=out` | S3 application-body bytes successfully returned by `ResponseWriter.Write`. |

Request metrics include successful responses, local validation/authz failures,
backend errors, and 501 responses. Health, readiness, metrics, and admin routes
are excluded. Bucketless ListBuckets uses `bucket=""` when labels are enabled.
When labels are disabled, every operation, including ListBuckets, uses `"*"`.

Inbound bytes include object data and XML request bodies actually read. Outbound
bytes include object data and XML success/error bodies actually written. They
exclude headers, TLS, HTTP framing, and internal server-side CopyObject data. A
range GET counts only its returned plaintext range. A stream failure after
headers retains the committed status while recording only successfully written
bytes. Counters ignore zero and reject negative inputs.

Rationale: new families preserve Prometheus compatibility while separating
client traffic from `encryption_bytes_total` crypto throughput and
`gateway_upload_part_copy_bytes_total` internal copy throughput.

### Metrics API

```go
func (m *Metrics) RecordS3ClientRequest(
    ctx context.Context, operation, bucket string, statusCode int,
)

func (m *Metrics) RecordS3ClientBytes(
    ctx context.Context, bucket, direction string, bytes int64,
)
```

Both methods use one private `bucketLabel(bucket string)` helper shared with
existing S3 metrics. `direction` is a closed internal set (`in`, `out`), never
caller-controlled arbitrary text. Exemplars may be attached to request counters;
byte counters do not require exemplars.

### HTTP instrumentation contract

```go
type s3ResponseRecorder interface {
    http.ResponseWriter
    StatusCode() int
    BytesWritten() int64
    Unwrap() http.ResponseWriter
}
```

The concrete wrapper records the first committed status, defaults to 200 on an
implicit write, and sums successful `Write` return values. It must preserve
`http.Flusher`, `http.Hijacker`, `http.Pusher`, `io.ReaderFrom`, and `Unwrap` so
`http.ResponseController` and streaming deadlines continue to work
(`internal/api/handlers.go:3308`).

Each route is registered through a wrapper with a fixed semantic operation. The
wrapper extracts `mux.Vars(r)["bucket"]`, installs one inbound-byte tracker, and
emits terminal status/in/out metrics in a deferred action. Ordinary bodies are
counted at the client-facing body. `STREAMING-*` PutObject and UploadPart bodies
are counted after `NewAwsChunkedReader` (`internal/api/handlers.go:1709`,
`internal/api/handlers.go:3571`) to exclude framing. Counting occurs before
seekable/retry buffers, so SDK retries do not multiply client input.

### Dashboard queries

```promql
sum by (bucket, direction) (
  rate(s3_client_bytes_total{namespace=~"$namespace",pod=~"$pod",bucket=~"$bucket"}[$interval])
)
```

```promql
sum by (bucket, operation, status_code) (
  rate(s3_client_requests_total{namespace=~"$namespace",pod=~"$pod",bucket=~"$bucket"}[$interval])
)
```

The dashboard adds a `$bucket` variable from `label_values` and an error-ratio
panel using `status_code=~"4..|5.."` divided by all statuses.

## 4. Work Breakdown

### Phase A — Metric families and compatibility guards

- **A1 — edit `internal/metrics/metrics.go`:** add the two CounterVec fields,
  register exact names/labels/help, add recording methods and shared bucket normalization.
- **A2 — edit `internal/metrics/metrics_test.go`:** test values, numeric status,
  disabled labels, invalid byte inputs, registration, nil safety, and unchanged
  descriptors for existing metrics.
- **A3 — edit `internal/metrics/cardinality_test.go`:** prove byte series are
  bounded by bucket/direction and request labels contain only fixed dimensions.

### Phase B — Central client-boundary instrumentation

- **B1 — new `internal/api/s3_instrumentation.go`:** implement transparent
  response recording, inbound tracker, body wrappers, and semantic route wrapper.
- **B2 — new `internal/api/s3_instrumentation_test.go`:** test implicit status,
  first-header behavior, optional interfaces, partial writes, and exact-once emission.
- **B3 — edit `internal/api/handlers.go`:** register every S3 route through the
  semantic wrapper; exclude system routes and assign stable operation names.
- **B4 — edit `internal/api/handlers.go`:** place input counters after AWS chunk
  decoding for PutObject/UploadPart and before encryption/seekable bodies.
- **B5 — edit `internal/api/handlers_test.go`:** cover plaintext, streaming,
  ranged, partial-write, retry, validation-error, and ListBuckets metrics.

Phase B depends on the APIs from Phase A.

### Phase C — Passthrough and semantic completeness

- **C1 — edit `internal/api/utils.go`:** make `copyProxyResponse` return actual
  count/error; let central recording remain authoritative for client bytes.
- **C2 — edit `internal/api/utils.go`:** on passthrough success record existing
  `RecordS3Operation`; on failure/backend error record existing `RecordS3Error`
  with bounded classification, without changing legacy HTTP metrics.
- **C3 — edit `internal/api/utils_test.go`:** test actual chunked response bytes,
  request-body input, semantic operation/error recording, and 502 status.
- **C4 — edit `internal/api/object_lock.go` and tests:** add existing semantic
  success/error parity while route wrapper supplies request/status/bytes.
- **C5 — edit `internal/api/upload_part_copy.go`:** retain internal-copy byte
  metrics and confirm the new client metric counts only request/response payloads.

### Phase D — Helm, dashboard, and docs

- **D1 — edit Helm values/schema/deployment descriptions:** clarify that
  `enableBucketLabel` controls all bucket-labelled S3 metrics; add chart tests.
- **D2 — edit `helm/s3-encryption-gateway/dashboards/s3-encryption-gateway.json`:**
  add bucket variable and throughput, request-status, and error-ratio panels.
- **D3 — edit dashboard tests:** assert variable and PromQL expressions exist.
- **D4 — edit `README.md`, `docs/OBSERVABILITY.md`, `docs/DEPLOYMENT.md`,
  `docs/RUNBOOK.md` and chart README:** document all
  traffic metric distinctions, cardinality, and example queries.
- **D5 — edit `CHANGELOG.md`:** add V1.0-OBS-2 under Unreleased.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Adding labels breaks dashboards | Add new metric families; do not alter existing descriptors. |
| Byte metrics report ciphertext/promised lengths | Count actual client reads/writes at the HTTP boundary. |
| AWS streaming framing inflates input | Count after `NewAwsChunkedReader`. |
| SDK retry rereads inflate input | Count before seekable/retry buffering. |
| Wrapper breaks streaming or deadlines | Preserve optional interfaces and `Unwrap`; test them explicitly. |
| One request emits multiple status increments | Centralize terminal emission in one route wrapper. |
| Bucket/key cardinality grows without bound | Use parsed bucket only; collapse to `*` when disabled; forbid dynamic labels. |
| Internal copies look like client traffic | Count only HTTP payload; retain dedicated UploadPartCopy metric separately. |

## 10. Follow-ups / Out-of-scope items surfaced during planning

- Evaluate per-bucket alert rules after production data establishes sensible
  thresholds; do not ship high-cardinality or noisy defaults now.
- Consider backend ciphertext network metrics separately if operators need
  provider billing visibility.
- Legacy HTTP path labels expose bucket-like cardinality; changing them needs a
  separate deprecation/migration plan.
