# V1.0-S3-7 — Fix ListBuckets 502 with Explicit Credential Permissions — Implementation Plan

Status: Verified Complete
Owner: API / Config / Compatibility

Labels: `area:api`, `area:config`, `area:compatibility`, `type:bug`

> Scope clarified relative to the Summary, Tests, and Definition of Done in
> `docs/issues/V1.0-S3-7.md`. Discovery found no code path by which valid
> object or lifecycle permission values alter backend routing. It did find that

## 1. Context & Current State

The reporter receives the gateway-generated `BadGateway` response from root
`aws s3 ls` when `GW_CRED_0_PERMISSIONS=rw` or
`GW_CRED_0_BUCKET_PERMISSIONS=create,delete` is present
as documented in `docs/issues/V1.0-S3-7.md`. These settings are independent in
the configuration model: `GatewayCredential` stores object permission and bucket
lifecycle grants in separate fields (`internal/config/config.go:772-788`), the
indexed environment loader populates them independently
(`internal/config/config.go:1820-1876`), and validation accepts `ro`/`rw` plus
`create`/`delete`/`manage` (`internal/config/config.go:831-861`). The immutable
credential snapshot defaults omitted object permission to `rw` and otherwise
copies both fields without changing backend configuration
(`internal/api/credential_store.go:91-112`).

ListBuckets authorization likewise does not explain a 502. Both middleware and
handler admit `ro` and `rw`; lifecycle grants are not inspected
(`internal/api/authorization.go:43-49`, `internal/api/handlers.go:6180-6190`).
The accepted authorization ADR requires exactly this behavior and requires a
deny-all scope to return an empty inventory (`docs/adr/0016-per-credential-authorization.md:11-30`). Existing tests already prove read-only access, empty
scope filtering, backend non-2xx proxying, and generic transport failure mapping
when credentials are manually assembled (`internal/api/handlers_test.go:3827-3875,4218-4336`). Existing environment tests cover selected fields but do
not exercise the reported permission matrix through effective credential
compilation (`internal/config/config_test.go:938-1017`).

The actionable defect is in the request path. `handleListBuckets` calls
`forwardToBackend`; only an error from that helper produces the reporter's exact
“upstream S3 backend returned an error” response
(`internal/api/handlers.go:6191-6207`). `forwardToBackend` passes the configured
endpoint directly to `url.Parse` and adds a scheme only when `u.Scheme == ""`
(`internal/api/utils.go:149-166`). For a common endpoint such as `rustfs:9000`,
Go parses `rustfs` as a scheme and leaves the host empty, so the `UseSSL=false`
fallback never runs and `http.Client.Do` fails before contacting RustFS. This
raw path also constructs a private minimal transport which omits the shared
default transport settings and configured backend CA/insecure diagnostics
(`internal/api/utils.go:247-258`).

GH-284 already established and implemented the correct backend contract:
scheme-less endpoints are normalized from `UseSSL`, explicit HTTP(S) schemes
win, and malformed/non-HTTP(S) endpoints are rejected
(`internal/s3/client.go:413-447`). `NewProxyClient` applies that normalization
and the shared TLS-aware transport (`internal/s3/proxy_client.go:25-55`), while
`newBackendHTTPTransport` clones the default transport and applies TLS settings
(`internal/s3/backend_transport.go:13-49`). The raw API forwarding path bypasses
both facilities. V1.0-S3-7 will make those backend primitives reusable by the
API path, add safe diagnostics, and prove the reporter's permission matrix
against a real RustFS fixture. This follows the single-source-of-truth principle
for configuration normalization and the standard practice of wrapping errors
while keeping sensitive request material out of logs [2][3].

## 2. Design Goals & Non-Goals

### Goals

1. **Endpoint parity** — raw API forwarding, SDK clients, and `ProxyClient`
   resolve scheme-less and explicit backend endpoints by one shared contract.
2. **Transport parity** — raw ListBuckets/passthrough requests honor backend CA,
   TLS verification, proxy, timeout, and connection-pooling behavior supplied
   by the shared backend transport constructor.
3. **Permission invariance** — omitted/default `rw`, explicit `rw`, and any
   valid lifecycle-grant combination produce identical ListBuckets routing;
   explicit `ro` also remains authorized.
4. **Scope invariance** — absent bucket scope returns all backend-visible
   buckets, while an explicitly empty scope returns HTTP 200 with an empty
   `<Buckets>` element.
5. **Actionable safe diagnostics** — forwarding failures record operation,
   endpoint scheme/host, and wrapped cause without credentials, authorization
   headers, secrets, or query values.
6. **Wire compatibility** — transport failures retain the existing XML 502;
   backend HTTP responses continue to be proxied unchanged.
7. **Real-provider proof** — a current pinned AWS CLI executes root `aws s3 ls`
   through the gateway to RustFS with the reported permission permutations.

### Non-Goals

1. **CRC64NVME upload support** — GH-283 owns the independent AWS-chunked
   `PutObject` failure; ListBuckets has no request body.
2. **Permission redesign** — ADR 0016 already defines object, lifecycle, and
   scope semantics; this issue preserves rather than changes them.
3. **New backend TLS options** — GH-285 introduced CA and insecure-diagnostic
   controls; this issue only makes the raw forwarding path honor them.
4. **Retry-policy changes** — preserving the existing raw forwarding response
   contract is sufficient; introducing retries could alter non-idempotent
   passthrough operations and requires separate design.
5. **Logging request headers or raw URLs** — these can contain signatures or
   sensitive query data and are unnecessary for diagnosis.

## 3. Target Interface / Semantics / Behaviour

### 3.1 Shared backend endpoint resolution

Add an exported internal-package resolver and retain the existing normalization
helper for current package-local callers:

```go
// ResolveEndpoint parses and validates a configured backend endpoint.
//
// Invariants:
//   - Explicit http:// and https:// schemes take precedence over useSSL.
//   - A scheme-less endpoint receives the scheme selected by useSSL.
//   - Only HTTP(S) URLs with a non-empty host are returned.
//   - The returned URL is newly allocated and safe for caller mutation.
func ResolveEndpoint(endpoint string, useSSL bool) (*url.URL, error)
```

| Configured endpoint | `UseSSL` | Result |
|---|---:|---|
| `rustfs:9000` | false | `http://rustfs:9000` |
| `rustfs:9000` | true | `https://rustfs:9000` |
| `http://rustfs:9000` | true | unchanged HTTP URL |
| `https://rustfs:9000` | false | unchanged HTTPS URL |
| empty, unsupported scheme, or missing host | either | error before dispatch |

The resolver centralizes an existing contract rather than creating a second
normalizer. Returning a parsed copy lets each request safely replace path and
query without mutating shared state [1].

### 3.2 Shared backend transport

Expose construction through the internal `s3` package:

```go
// NewBackendHTTPTransport builds the transport used for backend HTTP traffic.
// The caller owns the returned transport and may tune operation-specific
// timeout fields before first use.
func NewBackendHTTPTransport(cfg config.BackendTLSConfig) (*http.Transport, error)
```

The function keeps the current clone-of-`http.DefaultTransport` behavior,
TLS 1.2 minimum, custom root CA handling, and explicit insecure diagnostic mode
(`internal/s3/backend_transport.go:13-49`). Exporting this internal helper avoids
copying security-sensitive transport configuration into `internal/api`.

### 3.3 Raw forwarding contract

`forwardToBackend` keeps its signature:

```go
func (h *Handler) forwardToBackend(r *http.Request) (*http.Response, error)
```

It must resolve `h.config.Backend.Endpoint` with
`s3.ResolveEndpoint(endpoint, UseSSL)`, clone the returned URL, replace only
`Path` and `RawQuery`, strip inbound authentication artifacts, sign with backend
credentials, and dispatch through a transport from
`s3.NewBackendHTTPTransport(h.config.Backend.TLS)`. Errors must remain wrapped
with stage-specific context (`resolve backend endpoint`, `build backend
transport`, `sign backend request`, `send backend request`). Existing request
and response behavior in `internal/api/utils.go:168-259` otherwise remains
unchanged.

`handleListBuckets` must log a forwarding error before returning the existing
client response:

```go
h.logger.WithError(err).WithFields(logrus.Fields{
    "operation":      "ListBuckets",
    "backend_scheme": resolvedScheme,
    "backend_host":   resolvedHost,
}).Error("Failed to forward ListBuckets request to backend")
```

The implementation may derive scheme/host through a small safe helper; it must
never log userinfo, raw query, request headers, access keys, secrets, or the full
request URL. The external response remains:

| Condition | HTTP / S3 code | Body behavior |
|---|---|---|
| Authorization is not `ro` or `rw` | 403 `AccessDenied` | Existing authorization XML |
| Endpoint/transport/request failure | 502 `BadGateway` | Existing generic message; details only in sanitized logs |
| Backend returns non-2xx | Backend status/body | Proxy unchanged |
| Backend returns malformed/oversized 2xx XML | 502 `BadGateway` | Existing “invalid response” XML |
| Valid backend XML, absent scope | 200 | All backend-visible buckets |
| Valid backend XML, explicit empty scope | 200 | Empty `<Buckets>` inventory |

This separates operator diagnostics from the public error surface and prevents
backend topology or credentials from leaking to clients [2][3].

### 3.4 Credential behavior matrix

| `PERMISSIONS` | `BUCKET_PERMISSIONS` | `BUCKETS` | ListBuckets result |
|---|---|---|---|
| omitted (defaults `rw`) | omitted | absent | Forward and return visible buckets |
| `rw` | omitted | absent | Same as omitted/default |
| `ro` | omitted | absent | Same ListBuckets access as `rw` |
| omitted or `rw` | `create`, `delete`, or both | absent | Same as no lifecycle grants |
| omitted or `rw` | any valid set | explicitly empty | Forward, then return 200 with empty inventory |

The matrix is the executable form of ADR 0016. Lifecycle permissions control
bucket mutation only and cannot broaden or narrow ListBuckets.

## 6. Test Strategy

Testing follows `docs/TESTING.md`: Tier 1 tests have no build tag and never
start Docker; Tier 2 tests use only the `conformance` build tag and
Testcontainers with random mapped ports. Each test belongs to exactly one tier.
Docker/provider unavailability is a fixture-specific `t.Skip`, not a failure.
Conformance bodies are provider-neutral and gate only through capability bits;
the AST isolation/provider-name checks remain authoritative.

Unit tests isolate endpoint resolution, transport construction, configuration
loading, effective policy compilation, middleware authorization, handler
filtering, logging, and wire errors. The conformance case verifies the complete
signed AWS CLI request against real provider infrastructure. No benchmark or
fuzz test is required because the change adds no parser loop, unbounded input,
or performance-sensitive algorithm. Race coverage is supplied once by
`make test`.

## 7. Risks & Mitigations

| Risk | Mitigation |
|---|---|
| Exporting endpoint/transport helpers creates divergent callers later | Keep one implementation in `internal/s3`; make SDK, ProxyClient, and raw API forwarding consume it and test parity. |
| Replacing the raw transport changes proxy or connection behavior | Build from the existing clone-of-default transport, preserve context and response ownership, and run all passthrough/ListBuckets unit and conformance suites. |
| Diagnostic logs leak backend credentials or signed query material | Log only operation plus parsed scheme/host and wrapped transport error; add explicit negative assertions for secrets, Authorization, access key, and query values. |
| A test encodes the reporter's correlation as an unproven permission mutation | Test permissions as invariant inputs and endpoint normalization as the diagnosed cause; do not change ADR 0016 semantics without failing evidence. |
| Explicit empty scope is accidentally treated as unrestricted | Preserve nil-versus-empty slices through environment loading and credential compilation; assert HTTP 200 with an empty inventory. |
| Backend S3 errors become generic gateway 502 responses | Retain and execute `TestHandleListBuckets_BackendNon2xxProxiesThrough`. |
| GH-283 and this issue create duplicate AWS CLI pins | Reuse the package-level canonical pin; GH-283 owns version upgrades and Renovate management. |
| Provider differences hide the original defect | Require RustFS evidence from `make test-conformance-local` while keeping the case provider-neutral for broader regression detection. |
| A Docker-backed regression accidentally enters Tier 1 or depends on a fixed port | Keep it under the `conformance` build tag, derive the scheme-less endpoint from the Testcontainers fixture, and require `make test-isolation-check`. |
| An unrelated upstream RustFS defect is confused with a gateway regression | Record and classify the failing request according to `docs/TESTING.md`; do not hide it with provider-name branching or remove `CapCLIAWSCLI` without evidence that the capability itself is unsupported. |

## 10. Follow-ups / Out-of-scope items surfaced during planning

1. **HTTP client lifetime and pooling** — `forwardToBackend` currently builds a
   transport/client for each request. Reusing a handler-owned client would
   improve connection pooling but requires lifecycle and reload semantics; it
   is not necessary to fix endpoint correctness.
2. **Unified passthrough architecture** — raw API forwarding and `ProxyClient`
   still contain overlapping request construction/signing responsibilities.
   Consolidating them is a larger refactor and should not delay this regression
   fix.
3. **CRC64NVME uploads** — remain owned by GH-283 and its compatibility plan.
