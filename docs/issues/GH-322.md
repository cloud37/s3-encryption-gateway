### Summary
The default CORS mode forwards bucket CORS configuration requests and browser
preflights to the backend. This does not work with backends that lack the S3
bucket CORS API; gateway-generated encrypted upload responses also do not
inherit backend CORS headers. Add an opt-in `cors.mode: gateway` that stores
standard per-bucket S3 CORS XML in shared Valkey and evaluates both preflights
and actual response headers in the gateway. Keep `passthrough` as the default.

Planning clarification: gateway mode uses Valkey as its authoritative store.
Include an optional global fallback with explicitly configured origins, methods,
allowed headers and exposed headers for buckets without a CORS configuration,
and an optional global `allow_credentials` switch (both disabled by default).
The credentials switch applies to both bucket rules and fallback, echoing the
matched origin rather than `*`. The fallback is not a bucket CORS document.

### Valkey durability warning (release-blocking)
Gateway-managed CORS makes Valkey the **authoritative, durable source of truth**
for per-bucket CORS configuration. Bucket rules are created, replaced, and
deleted at runtime through the authenticated S3 `PUT/GET/DELETE /{bucket}?cors`
API. They have no TTL and are **not** reloaded from files on startup. File-based
policies may be useful as operator-maintained templates or a re-apply process,
but cannot transparently restore subsequent API changes.

In `passthrough` mode the gateway does not store bucket CORS rules in Valkey.
In `gateway` mode, **do not treat Valkey as disposable cache**: enable durable
storage/persistence and tested backups before enabling the feature in production.
An empty/reset Valkey loses the CORS documents permanently unless restored from
backup or re-applied. Once Valkey is healthy but empty, gateway readiness can
still pass: `GET ?cors` reports `NoSuchCORSConfiguration`, unmatched preflights
return 403, and actual responses lack CORS headers. Browser uploads may fail
even though signed non-browser S3 operations still work. If the optional
global fallback is configured it applies to those now-missing documents;
it can grant broader cross-origin access than the lost per-bucket policies.
Do not conflate transient Valkey unavailability (fail-closed, 503 preflight)
with data loss (missing-key behavior). Production documentation and release
notes must state these consequences prominently. A startup persistence check
may **warn**, not block: AOF/RDB status cannot prove backups are recoverable.

### Implementation Guide
- [x] Keep passthrough behavior unchanged by default; require Valkey for gateway mode.
- [x] Validate and persist ordered bucket CORS rules with a bounded XML body.
- [x] Evaluate first-match rule for OPTIONS and actual requests without backend preflight round trips.
- [x] Apply response headers to encrypted, plaintext, and passthrough paths; prevent upstream CORS headers from overriding gateway policy.
- [x] Support optional fallback origins and explicitly enabled credentials safely.
- [x] Warn on missing/unverifiable Valkey persistence in gateway mode, and publish explicit backup/restore and reset-impact guidance; do not refuse startup solely on that warning.
