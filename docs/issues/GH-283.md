### Summary
AWS CLI v2.34.32 enables upload integrity protection by default and sends
AWS-chunked uploads whose declared trailer is `x-amz-checksum-crc64nvme`.
The gateway's strict AWS-chunked verifier supports CRC32, CRC32C, SHA-1, and
SHA-256 trailers but rejects CRC64NVME before forwarding the request, returning
`InvalidRequest: The AWS-chunked request body is invalid.`

Accept and verify CRC-64/NVME trailers with the same fail-closed behavior as
the existing checksum algorithms. Keep compatibility clients and maintained
provider images on explicit versions, with Renovate proposing every available
upgrade so the existing pull-request conformance matrix detects upstream
regressions before a new version is merged.

### Implementation Guide
- [x] Add `x-amz-checksum-crc64nvme` to the strict allowed trailer set.
- [x] Feed each verified-body read into a streaming CRC-64/NVME hash.
- [x] Base64-decode the trailer, require exactly eight bytes in big-endian order, and compare it with the computed checksum.
- [x] Preserve fail-closed rejection of undeclared, malformed, duplicate, and mismatched trailers.
- [x] Pin AWS CLI at or above 2.34.32 and use explicit release tags for every maintained conformance client/provider image; eliminate mutable tags from other test fixtures.
- [x] Add Renovate custom extraction rules so each maintained Go-source image and embedded Python client pin receives update PRs; explicitly exempt the frozen MinIO baseline.
- [x] Require image-update PRs to run the existing provider conformance and compatibility matrices, and retain those named checks in branch protection before merge.

### Cross-references
- GitHub issue #283 and follow-up analysis supplied by the maintainer.
- V1.0-S3-7 tracks the reporter's separate root `aws s3 ls`
  (`ListBuckets`) 502 with explicitly setting `GW_CRED_0_PERMISSIONS=rw`
  and/or `GW_CRED_0_BUCKET_PERMISSIONS=create,delete`. That request has no
  AWS-chunked body and is not fixed by CRC64NVME support. Current authorization
  semantics allow ListBuckets for `ro` and `rw` and do not consult bucket
  lifecycle grants, so this requires a separate forwarding/configuration
  reproducer rather than a change to those permission meanings.
- An explicitly present but empty `GW_CRED_0_BUCKETS` means deny-all, not
  unrestricted access. For ListBuckets that should yield HTTP 200 with an empty
  `<Buckets>` result after backend filtering; it does not explain the reported
  `BadGateway` response.
- GH-284 fixed scheme selection for the primary backend clients. V1.0-S3-7
  tracks the remaining raw ListBuckets forwarding path for the reporter's
  intended-HTTP, scheme-less `rustfs:9000` endpoint.
- The separate `Content-Encoding: aws-chunked, gzip` compatibility restriction is not required to reproduce #283.
