## [V1.0-AUTH-2] Per-Credential Bucket Scoping and Authorization
- Owner: Security / API
- Priority: P0
- Status: **PLANNED — plan ready**
- Labels: `milestone:v1.0`, `area:security`, `area:api`, `area:config`
- Plan: `docs/plans/V1.0-AUTH-2-plan.md`
- GitHub Issue: https://github.com/cloud37/s3-encryption-gateway/issues/229

### Summary
Extend gateway-managed credentials with exact and constrained trailing-wildcard
bucket scopes, object permissions (`ro` or `rw`), and independent explicit
bucket-management permissions (`create` and `delete`). Authorization must run
after signature validation and before any backend access. Copy operations must
authorize both source and destination buckets, while `ListBuckets` must filter
the backend inventory to the credential's effective scope.

### Compatibility and security contract
- Omitted `buckets` preserves existing unrestricted credential behavior.
- Explicit `buckets: []` denies access to all buckets.
- Patterns are exact names or one trailing `*` prefix pattern such as `app-*`.
- Omitted `permissions` defaults to `rw`; `rw` never implies bucket creation or deletion.
- `PROXIED_BUCKET` intersects with, and never widens, credential scope.
- Authorization denials return S3 `AccessDenied` without contacting the backend.
- Credential and authorization changes are atomically hot-reloadable.

### Definition of Done
- [ ] Exact, wildcard, omitted, and explicit-empty bucket scopes are validated and enforced.
- [ ] Read-only credentials cannot mutate objects or bucket subresources.
- [ ] CopyObject and UploadPartCopy authorize source read and destination write before backend access.
- [ ] ListBuckets returns only the effective credential/global bucket intersection.
- [ ] Invalid reloads retain the prior complete credential snapshot.
- [ ] YAML, indexed environment variables, credentials files, Helm values, audit events, and docs are updated.

## [V1.0-S3-5] Authorized Optional Bucket Management Passthrough
- Owner: S3 Compatibility / Security
- Priority: P1
- Status: **BLOCKED — depends on V1.0-AUTH-2; plan ready**
- Labels: `milestone:v1.0`, `area:s3-api`, `area:security`, `area:config`
- Plan: `docs/plans/V1.0-S3-5-plan.md`
- GitHub Issue: https://github.com/cloud37/s3-encryption-gateway/issues/231
- Depends on: V1.0-AUTH-2

### Summary
Replace the unconditional CreateBucket `501 NotImplemented` behavior with an
opt-in backend passthrough. Creation is allowed only when the global safe-default
gate is enabled, the authenticated credential scope matches the target bucket,
and the credential explicitly grants `bucket_permissions: [create]`. DeleteBucket
requires matching scope and the independent explicit `delete` permission.

### Authorization contract
```text
CreateBucket = ALLOW_BUCKET_CREATION
               AND target bucket is in effective scope
               AND bucket_permissions contains create

DeleteBucket = target bucket is in effective scope
               AND bucket_permissions contains delete
```

### Definition of Done
- [ ] `ALLOW_BUCKET_CREATION` defaults to false.
- [ ] Unauthorized or disabled requests never contact the backend.
- [ ] `rw` object permission grants neither create nor delete.
- [ ] Authorized CreateBucket preserves the request body, including LocationConstraint, and backend response semantics.
- [ ] Bucket names are validated before forwarding.
- [ ] DeleteBucket requires explicit delete permission.
- [ ] Unit, Helm, and provider-capability-gated conformance tests pass.

## [V1.0-S3-4] Protect Gateway-Owned MPU Metadata From Client Deletion
- Owner: S3 Compatibility
- Priority: P1
- Status: **OPEN — follow-up from issue #217**
- Labels: `milestone:v1.0`, `area:compat`, `area:mpu`

### Summary
Encrypted multipart objects depend on gateway-owned `.mpu-manifest` companion
objects. Client-facing listings no longer expose these objects, but direct
DeleteObject and DeleteObjects requests can still remove them and make the
associated encrypted object unreadable.

### Scope
- Reject or otherwise guard client deletion of a manifest while its main object exists.
- Preserve internal manifest cleanup when the main object is deleted.
- Define an explicit administrative/recovery path for intentional manifest cleanup.
- Add unit and Tier 2 conformance coverage for single and batch deletion.

## [V1.0-S3-6] Centralize Encrypted Object Metadata Handling
- Owner: S3 Compatibility / Crypto / API
- Priority: P1
- Status: **OPEN — follow-up from issue #236**
- Labels: `milestone:v1.0`, `area:compat`, `area:crypto`, `area:api`

### Summary
Standard object metadata for encrypted objects currently crosses several
independent paths: direct and multipart writes, copy destinations, chunked and
non-chunked decryption, and HEAD, GET, and ranged-GET response writers. Issue
#236 showed that independently restoring the same values in each path allows a
correct fix in one path to leave another path returning ciphertext metadata.

Investigate all metadata transformations before choosing a shared abstraction.
The intended outcome is one canonical persistence path for plaintext metadata
on encrypted writes and one canonical response-decoration path for encrypted
reads, without changing S3 response semantics or authenticated encryption
metadata.

### Investigation scope
- Inventory every write path: PutObject, CopyObject, CreateMultipartUpload /
  CompleteMultipartUpload, UploadPartCopy, encrypted metadata fallback, and
  metadata compaction.
- Inventory every read path: HeadObject, GetObject, full and ranged chunked
  GET, MPU GET and ranged MPU GET, cache hits, and response override query
  parameters.
- Define the ownership and precedence of native S3 headers, `x-amz-meta-*`
  user metadata, encryption metadata, compacted metadata, and encrypted
  metadata blobs.
- Identify additional duplicated metadata transformations suitable for
  centralization, including plaintext content length and ETag restoration.
- Preserve request-header overrides and S3 `x-amz-metadata-directive: REPLACE`
  semantics.

### Definition of Done
- [ ] A written inventory maps each metadata field and transformation to all
  write and read paths, including cache and range responses.
- [ ] A minimal shared write-side persistence mechanism is introduced and used
  by every encrypted object creation path.
- [ ] A minimal shared read-side response decorator is used by HEAD, GET,
  ranged GET, MPU GET, and cache responses.
- [ ] Standard metadata precedence is documented and covered by unit tests.
- [ ] Provider-agnostic conformance tests cover direct PUT, CopyObject,
  multipart, UploadPartCopy, full GET, ranged GET, and HEAD for chunked and
  non-chunked self-contained encryption.
- [ ] Existing encrypted objects remain readable and objects written by older
  releases retain their documented fallback behavior.

## [V1.0-SEC-43] Verify Non-Streaming SigV4 Payload Integrity
- Owner: Security / API
- Priority: P0
- Status: **PLANNED — plan ready**
- Labels: `milestone:v1.0`, `area:security`, `area:api`, `area:auth`
- Plan: `docs/plans/V1.0-SEC-43-plan.md`

### Summary
SigV4 authentication currently signs the client-declared
`X-Amz-Content-Sha256` value but does not compare a concrete SHA-256 digest
with the non-streaming request body. A body modified after signing is therefore
accepted and can be encrypted or re-signed with the gateway's backend
credentials. Centrally spool, hash, and verify each authenticated concrete
payload before routing, encryption, backend access, cache updates, or multipart
state mutation. `UNSIGNED-PAYLOAD` remains intentionally exempt.

### Affected
- `internal/api/auth.go` — retain the authenticated concrete payload digest.
- `internal/api/auth_middleware.go` — verify and replace the request body before dispatch.
- `internal/api/verified_aws_body.go` — share the bounded-disk spool lifecycle.
- `internal/api/errors.go` — preserve opaque S3 error mapping.
- `internal/api/handlers.go` and `internal/api/utils.go` — prove all mutation paths consume only verified bytes.

### Definition of Done
- [ ] Every header-authenticated SigV4 body with a concrete lowercase SHA-256 digest is fully hashed and compared before downstream dispatch.
- [ ] A mismatch returns `SignatureDoesNotMatch` and causes no backend, encryption, cache, or MPU-state mutation.
- [ ] Verified bodies are replayable from a mode-0600 temporary file and are removed on success, failure, and cancellation.
- [ ] `UNSIGNED-PAYLOAD` and existing verified AWS-chunked modes preserve their documented semantics without double spooling.
- [ ] Unit and provider-agnostic conformance tests cover valid, tampered, empty, canceled, and spool-failure cases.

## [V1.0-SEC-44] Authenticate SigV2 S3 Subresources
- Owner: Security / API / Configuration
- Priority: P1
- Status: **PLANNED — plan ready**
- Labels: `milestone:v1.0`, `area:security`, `area:api`, `area:auth`, `area:config`
- Plan: `docs/plans/V1.0-SEC-44-plan.md`

### Summary
SigV2 canonicalization currently signs only the request path, allowing an
attacker to add, remove, or change routing-sensitive S3 subresources without
invalidating a gateway-valid signature. Implement deterministic canonicalized
resource construction for the AWS SigV2 signed-subresource and response-
override allowlist, extended for gateway-supported operation selectors. Reject
ambiguous duplicates and disable deprecated SigV2 by default while retaining
an explicit compatibility opt-in.

### Affected
- `internal/api/auth.go` — canonicalize signed subresources for both SigV2 authentication forms.
- `internal/config/config.go` — default SigV2 off and implement the documented environment override.
- `internal/api/handlers.go` — source of routing-sensitive query semantics.
- `config.yaml.example` and Helm chart files — document and expose explicit SigV2 opt-in.

### Definition of Done
- [ ] Adding, removing, substituting, or changing every signed routing-sensitive subresource invalidates SigV2 authentication.
- [ ] Canonical resources preserve escaped paths, sort exact case-sensitive names, include values when present, and reject duplicate signed parameters.
- [ ] Ordinary non-subresource query parameters remain compatible with the SigV2 specification.
- [ ] SigV2 defaults to disabled in binary and Helm configuration and can be explicitly enabled through YAML or environment configuration.
- [ ] Unit, Helm, and provider-agnostic conformance tests cover header and presigned SigV2 requests.
