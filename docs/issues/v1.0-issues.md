# Milestone v1.0 — Issue Tracker and Implementation Guide

This document tracks issues for v1.0 with implementation guides and validation criteria derived from `docs/ROADMAP.md`.

## Scope and Goals
- Security/Crypto: Full KMS production readiness (HA, caching, failure modes); sensitive data zeroization and constant-time comparisons audit
- S3 Compatibility: Broad feature parity (tagging, ACLs, lifecycle headers passthrough); SDK/tool compatibility certification matrix
- Performance & Scalability: Horizontal scale guidance; tuned HPA/SLOs; high-throughput benchmarks
- Observability: Turnkey dashboards (Grafana) and alerting rules
- Operations: Multi-arch images, SBOMs, provenance (SLSA); Helm chart on Artifact Hub with automated checks
- Ecosystem: Additional backends via shims (GCS, Azure Blob, filesystem); CLI for local testing (presign, quick put/get)

## Milestone Acceptance Criteria
- Compatibility certification matrix completed for targeted SDKs/tools.
- Published dashboards and alerting rules; documented SLOs and autoscaling guidance.
- Supply-chain artifacts for releases (multi-arch, SBOM, provenance) available.

## [V1.0-AUTH-2] Per-Credential Bucket Scoping and Authorization
- Owner: Security / API
- Priority: P0
- Status: **✅ VERIFIED COMPLETE**
- Labels: `milestone:v1.0`, `area:security`, `area:api`, `area:config`
- Plan: `docs/plans/V1.0-AUTH-2-plan.md`
- GitHub Issue: https://github.com/cloud37/s3-encryption-gateway/issues/229

### Summary
Extend gateway-managed credentials with exact and constrained trailing-wildcard
bucket scopes, object permissions (`ro` or `rw`), and independent explicit
bucket-management permissions (`create` and `delete`). Authorization must run
after signature validation and before any backend access. Copy operations must
authorize both source and destination buckets, while `ListBuckets` must filter
the backend inventory to the credential's effective scope.

### Compatibility and security contract
- Omitted `buckets` preserves existing unrestricted credential behavior.
- Explicit `buckets: []` denies access to all buckets.
- Patterns are exact names or one trailing `*` prefix pattern such as `app-*`.
- Omitted `permissions` defaults to `rw`; `rw` never implies bucket creation or deletion.
- `PROXIED_BUCKET` intersects with, and never widens, credential scope.
- Authorization denials return S3 `AccessDenied` without contacting the backend.
- Credential and authorization changes are atomically hot-reloadable.

### Definition of Done
- [x] Exact, wildcard, omitted, and explicit-empty bucket scopes are validated and enforced.
- [x] Read-only credentials cannot mutate objects or bucket subresources.
- [x] CopyObject and UploadPartCopy authorize source read and destination write before backend access.
- [x] ListBuckets returns only the effective credential/global bucket intersection.
- [x] Invalid reloads retain the prior complete credential snapshot.
- [x] YAML, indexed environment variables, credentials files, Helm values, audit events, and docs are updated.

## [V1.0-S3-6] Centralize Encrypted Object Metadata Handling
- Owner: S3 Compatibility / Crypto / API
- Priority: P1
- Status: **OPEN — follow-up from issue #236**
- Labels: `milestone:v1.0`, `area:compat`, `area:crypto`, `area:api`

### Summary
Standard object metadata for encrypted objects currently crosses several
independent paths: direct and multipart writes, copy destinations, chunked and
non-chunked decryption, and HEAD, GET, and ranged-GET response writers. Issue
#236 showed that independently restoring the same values in each path allows a
correct fix in one path to leave another path returning ciphertext metadata.

Investigate all metadata transformations before choosing a shared abstraction.
The intended outcome is one canonical persistence path for plaintext metadata
on encrypted writes and one canonical response-decoration path for encrypted
reads, without changing S3 response semantics or authenticated encryption
metadata.

### Investigation scope
- Inventory every write path: PutObject, CopyObject, CreateMultipartUpload /
  CompleteMultipartUpload, UploadPartCopy, encrypted metadata fallback, and
  metadata compaction.
- Inventory every read path: HeadObject, GetObject, full and ranged chunked
  GET, MPU GET and ranged MPU GET, cache hits, and response override query
  parameters.
- Define the ownership and precedence of native S3 headers, `x-amz-meta-*`
  user metadata, encryption metadata, compacted metadata, and encrypted
  metadata blobs.
- Identify additional duplicated metadata transformations suitable for
  centralization, including plaintext content length and ETag restoration.
- Preserve request-header overrides and S3 `x-amz-metadata-directive: REPLACE`
  semantics.

### Definition of Done
- [ ] A written inventory maps each metadata field and transformation to all
  write and read paths, including cache and range responses.
- [ ] A minimal shared write-side persistence mechanism is introduced and used
  by every encrypted object creation path.
- [ ] A minimal shared read-side response decorator is used by HEAD, GET,
  ranged GET, MPU GET, and cache responses.
- [ ] Standard metadata precedence is documented and covered by unit tests.
- [ ] Provider-agnostic conformance tests cover direct PUT, CopyObject,
  multipart, UploadPartCopy, full GET, ranged GET, and HEAD for chunked and
  non-chunked self-contained encryption.
- [ ] Existing encrypted objects remain readable and objects written by older
  releases retain their documented fallback behavior.

## [V1.0-CONFIG-1] Per-Bucket Encryption Bypass + Flat ENV Policy Configuration ✅ DONE
- Owner: Config / DX / Crypto
- Priority: P2
- Status: **✅ VERIFIED COMPLETE**
- Labels: `milestone:v1.0`, `area:config`, `area:crypto`, `area:dx`
- Plan: `docs/plans/V1.0-CONFIG-1-plan.md`
- GitHub Issue: https://github.com/cloud37/s3-encryption-gateway/issues/196

### Summary
The gateway currently encrypts **every** object unconditionally. There is no mechanism to tell the gateway "do not encrypt data going into this bucket." The policy system (`PolicyConfig`) allows per-bucket key/algorithm selection and MPU opt-out, but has no `disable_encryption` flag. The only existing bypass-like mechanism, `encrypt_multipart_uploads: false`, only affects the Valkey/DEK MPU path — single-PUT objects are still encrypted.

The user in issue #196 wants to store Restic backups (already encrypted client-side) without a second encryption layer. Without a bypass, they must run two separate gateway instances.

This issue introduces:
1. **`disable_encryption: true`** in `PolicyConfig` — makes the gateway store and serve objects as plain bytes for matching buckets.
2. **`PassthroughEngine`** — a no-op `crypto.EncryptionEngine` (Encrypt = identity; Decrypt = identity for plaintext objects, error for encrypted objects).
3. **Flat indexed env vars** (`GW_POLICY_N_*`) covering **all** `PolicyConfig` fields, modelled after the existing `GW_CRED_N_*` pattern — no file mount required, works in Kubernetes/Docker/Compose.

### Affected
- `internal/config/policy.go` — `DisableEncryption bool` field; `BucketDisablesEncryption()`; updated `BucketEncryptsMultipart`; conflict validation; `Reset()`; `LoadPoliciesFromEnv()`
- `internal/crypto/passthrough.go` — new: `PassthroughEngine` + `ErrEncryptedObjectInBypassBucket`
- `internal/crypto/engine.go` — extract `IsEncryptedMetadata` as package-level function
- `internal/api/handlers.go` — `getEncryptionEngine` bypass branch; error translation for `ErrEncryptedObjectInBypassBucket`
- `internal/config/config.go` — `loadFromEnv` gains `GW_POLICY_N_*` parsing loop
- `cmd/server/main.go` — env-policy wiring at startup and hot-reload
- `config.yaml.example` — `disable_encryption` annotation; `GW_POLICY_N_*` usage example
- `helm/s3-encryption-gateway/values.yaml` — document `disable_encryption` and `GW_POLICY_N_*`

### ENV var contract (all PolicyConfig fields)
```
GW_POLICY_N_ID                        string   (required to define policy N)
```
