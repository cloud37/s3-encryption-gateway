### Summary
Version 0.12.3 rejects S3 browser `POST Object` uploads because authentication
does not read multipart form credentials, authorization classifies bare
bucket POST as unknown, and no form-upload handler exists. This blocks Outline
and other applications using boto3 `generate_presigned_post` or AWS JavaScript
`createPresignedPost`. S3 multipart-upload initiation/completion is unrelated
to this HTML `multipart/form-data` operation.

### Approved scope
The user selected broader POST support, including redirects, XML tagging,
storage class, plaintext checksums, configured session credentials, and backend
SSE-S3/KMS/SSE-C. Implement SigV4 path-style single-file POST, exact/prefix/range
conditions with complete field coverage, filename expansion, standard/user
metadata, ACLs, 200/201/204 and 303 responses, and bounded pre-write validation.
Use the existing shared encryption/metadata pipeline rather than backend form
passthrough. Policy, credential scope/write permission, and PROXIED_BUCKET must
all permit the destination.

SSE is an additional backend encryption layer, not a replacement for gateway
encryption. SSE-C includes subsequent GET/HEAD/range and integrity-preflight
key propagation; customer keys must never enter persistent metadata or caches.
Accept direct TLS or an exact HTTPS indication from an explicitly trusted
immediate proxy, and require verified HTTPS to the backend. Untrusted forwarding
headers and SERVER_FORCE_HTTPS alone cannot establish secure transport.

GH-353 depends on GH-322 for browser response CORS, including auth errors.
Preserve the existing GH-322 issue/plan and consume its CORS store/middleware
instead of implementing a competing authority. Anonymous POST, SigV2 POST,
virtual-host bucket addressing, STS issuance, DevPay, directory buckets,
DSSE-KMS, SSE-C copy/MPU extensions and durable plaintext checksum APIs are
excluded; optional unsupported requests fail explicitly before mutation.
